# Answer an inbound text

**Type:** process · **Mark:** live · **Checked:** 2026-10-14 @ c48491d · **Where:** `app/Actions/RecordInbound.php:49` to `app/Actions/RunFrontDesk.php:115`

**One sentence.** A customer's text is recorded, claimed once with any texts sent just after it, answered by the agent, judged by the send rule, and then either sent as one reply (the owner's own price or offer sentences, the model's words, or both) or kept as a draft for the owner, with the customer always getting a line back.

**Input, movement, output.** Input: one inbound text from a provider webhook. Movement: record, claim, ask the agent, pick the owner's sentences, decide, send or hold. Output: a `messages` row for the text, usually one row for the answer (sent, or a draft with its verdict), sometimes a second automated text beside a draft, maybe intake answers, a pause, and owner alerts.

**Why this shape.** Each stage is guarded by a database claim, not a queue promise, so a retried webhook, a failed-open debounce and the sweep can never answer one text twice (D-42, `ClaimInboundBurst.php:12-20`). The agent has no tools: it only proposes words, a label and a few flags, and code decides whether anything goes out (`FrontDeskAgent.php:15-19`). Prices and offers are the owner's own sentences, picked and sent by code without asking Jev, because the model only names the service (D-04). The danger text skips the wait on purpose (D-17).

## Steps
1. **Record.** The webhook calls `RecordInbound::handle` (`TwilioTextWebhookController.php:24`, `FakeTextWebhookController.php:21`). One transaction finds or makes the contact, finds or opens the conversation, stores the text as `received` and writes a timeline entry (`RecordInbound.php:127-184`). A text the provider already delivered returns the stored row (`:51-57`). STOP, START and HELP end here (`:76-81`; see [contact-opt-out](../objects/contacts/contact-opt-out.md)).
2. **Safety line.** A text whose words describe gas, fire or water danger queues `RespondToLifeSafety` at once (`RecordInbound.php:109-121`, `RespondToLifeSafety.php:54`). `SendLifeSafetyLine` sends the fixed line, pauses and alerts (`SendLifeSafetyLine.php:58`, the send at `:95`, the pause and the alert at `:113-114`). A safety line that fails, with any error, still pauses and alerts the owner, with the reason (`:107-114`); so does a wait for the send lock that runs out (`gate.life_safety.lock_wait_seconds`, `:63-70`, `config/gate.php:142`); a retry that finds the line already sent sends no second one but finishes the pause and the alert if no alert is on file for that text (`finishHandOff`, `SendLifeSafetyLine.php:84-87`, `:127-140`); so does `RespondToLifeSafety` failing for good (`failed()`, `RespondToLifeSafety.php:72-88`, with its own `$timeout` of 120 seconds at `:39`; the alert says "could not be sent" or, when the line did go out, "sent, but check the conversation was paused"). `RunFrontDesk` takes a second look at step 6.
3. **Queue once.** `DispatchInbound::handle` flips `dispatched_at` with a conditional update and only then queues `ProcessInbound` (`DispatchInbound.php:32-53`). A push that fails gives the claim back, setting `dispatched_at` to null, and rethrows, so the provider's retry or the sweep queues the text later (`:49-52`); the push is not deferred with `afterCommit()`, so a caller's transaction cannot move it outside that `try` (WR-04). `SweepUndispatched` re-sends texts recorded but never queued, aged 2 minutes to 24 hours (`SweepUndispatched.php:25-38`, scheduled `routes/console.php:14`).
4. **Wait for the burst.** `ProcessInbound` waits about 20 seconds after the last text, 90 at most (`ProcessInbound.php:32`).
5. **Claim.** `ClaimInboundBurst::handle` sets `handled_at` on each unclaimed customer text, one atomic update per row (`ClaimInboundBurst.php:22-39`). Nothing claimed: stop. No SMS text in the burst: stop (`ProcessInbound.php:95`). No live folder version yet: the burst is claimed and left quietly (`:101-102`). Any other error inside the run is logged, then a note and an owner alert are written through `ReportFrontDeskFailure` (`:103-107`); a run that times out or whose worker dies does the same from `failed()` (`:142-165`, `$failOnTimeout` at `:50`), reporting the newest claimed SMS text at or before the one that queued the job (WR-03). `ReportFrontDeskFailure` skips a text it already reported, so the owner hears once per text (`ReportFrontDeskFailure.php:33-40`). The burst stays claimed in every case, so the customer cannot get two replies.
6. **Early exits in `RunFrontDesk::handle`** (`RunFrontDesk.php:115-142`), in order: second look at danger (`:117`, `answerDanger` `:879`); opted out, so alert the owner (`:119`); paused, so alert once per burst (`:125`); reply cap reached, so pause and alert (`:131`); plain words asking for a person, so hand off: alert, fixed handoff reply, pause (`:138`, `handOffToOwner` `:942-947`).
7. **Ask the agent.** `AgentFile::forChannel('sms')` (`RunFrontDesk.php:144`) and the conversation's live draft, if there is one, read as the **waiting draft** (`:152`) go to `RunFrontDeskAgent`, which tries each model in file order (`RunFrontDeskAgent.php:59`; see [agent-file-and-version](../objects/folder/agent-file-and-version.md)). It starts no further fallback once the next one could not finish inside `gate.agent.chain_budget_seconds`, and never reorders the chain (`RunFrontDeskAgent.php:60-68`, `:95-98`, `config/gate.php:103`). No agent for texts, and every model failing, each write a note and alert the owner through `ReportFrontDeskFailure::handle` (`ReportFrontDeskFailure.php:31`), then stop (`RunFrontDesk.php:144-150`, `:154-160`). The agent wanting a person: hand off (`:162-166`). The model is told the time now in the business's zone, in a Right now section last in its instructions (`FrontDeskPrompt.php:113`, `:292-298`), and each earlier text in the thread starts with its send time in brackets (`FrontDeskPrompt.php:139`, `:165`, `:304-309`); both are built at `RunFrontDeskAgent.php:52-53`. When a draft waits, the instructions also carry an Already with the owner section, which quotes the customer's own words that draft answered, never the draft (`FrontDeskPrompt.php:105-107`, `:233-262`). The burst it answers carries no time, because the same words also go to Jev and to the asks-for-a-person check (`FrontDeskPrompt.php:191-194`, `RunFrontDesk.php:138`, `:180`). Besides the words and the label, the model fills six proposal fields: the services whose price was asked, whether a discount was asked, and, only when a question waits, whether the text touches it, a check-in or added-info note, and an easy part to answer alone (`FrontDeskAgent.php:68-73`, read by `AgentReply.php:68-81`). Code decides what each one means.
8. **Keep what it learned.** Intake answers (`RunFrontDesk.php:168`, [intake-answer](../objects/intake/intake-answer.md)) and an empty contact name (`:169`) are stored before the send rule runs, even if the reply is then held.
9. **Pick the owner's sentences (code, no Jev).** For each service the customer asked a price for, plus each one still pending from the previous run (`pendingPriceSlugs`, `RunFrontDesk.php:726-738`), `PriceSentencePicker::pick` (`PriceSentencePicker.php:43`, through `pickPrices`, `RunFrontDesk.php:697`) returns one outcome (`PricePick.php:13-19`): send the owner's sentence, ask the customer's intake answers first (price pending), hold because no sentence is on file (or the owner quotes that price himself), or nothing. The model only names the service; the sentence is read from the live version (`RunFrontDesk.php:171-174`). A sentence the customer was told already is not repeated unless they ask again, and then it goes behind the owner's lead for same, higher, lower or changed (`PriceSentencePicker.php:144-162`, `sentenceText` `RunFrontDesk.php:713`, `FixedReplies::priceLead` `FixedReplies.php:83`); a corrected answer re-sends right away with a lead (`PriceSentencePicker.php:54`, `:128-137`, `:156`). When the customer asked for a discount, the sentence of every offer live today in the business's zone joins them (`OfferSentences::liveToday`, `OfferSentences.php:25`, `RunFrontDesk.php:175`). The result is a list of code sentences, which the sync already checked, so they are sent without Jev (`RunFrontDesk.php:176-177`).
10. **Decide the model's words.** The model's words still decide as before: `ComposeAutomatedText::forReply` adds disclosure and sign-off (`ComposeAutomatedText.php:26`, `RunFrontDesk.php:206`); `DecideSendOrDraft::decide` returns the verdict (`:207`), with the label guard when a booking draft waits (`labelGuardFor`, `:336-339`). A blank reply is accepted only for a price or discount ask (`AgentReply.php:54-56`). When the sentences fully answer it, or it is a check-in on a waiting draft, there are no words to judge (`RunFrontDesk.php:188`, `:196-198`); when code cannot answer it, it is held without words as `price:no_sentence` or `discount:no_live_offer` (`:199-204`). A classifier-found danger sends the safety line and drops the sentences (`:210-215`); Jev reading "asks for a person" hands off (`:216-219`). Each of Jev's price, promise, discount and complaint answers is read against its own bar (D-56), in `TriageReading.php:61-65`, from the classifier block of `config/gate.php:71-80`. A price that has no sentence, or a discount with no live offer, turns a verdict that would send into a hold, so the question still reaches the owner (`RunFrontDesk.php:222-226`).
11. **No draft waiting: one text.** Sentences alone when the model had no words: sent as a code answer, Jev not asked (`RunFrontDesk.php:190-194`, `sendCodeAnswer` `:797`). Sentences plus the model's words when the words pass, as one text (`sendPassingReply`, `:350`, through `SendCombinedReply` whenever sentences or a fixed line ride, `:353-363`). When the words are held, they become the draft and the sentences still go out at once with the owner's partial holding line, or with the owner's complaint reply leading if the words were a complaint (`:280-291`, `sendPartialHolding` `:661-686`, complaint arm `:667-669`). No sentences: verdict `send` goes out through `OutboundSender::send` (`:353-362`); a channel failure alerts the owner (`alertAboutFailedSend`, `:854-870`), a carrier opt-out alerts the owner to call, any other refusal becomes a `send_refused` draft (`:364-369`). Verdict `hold`: `storeDraft` withdraws any older draft and writes the new draft with its timeline entry in one transaction (`:1011-1055`), alerts the owner after commit (`:1059-1061`), and sends one holding reply unless the conversation is paused or the verdict found a danger (`:1063-1065`). Whatever is assembled is measured as the customer would get it, and the model's words are held `too_long` if the whole text passes 1,600 characters (`SendCombinedReply.php:68`, `SendOwnerReply.php:20`, `RunFrontDesk.php:264-266`).
12. **A draft is waiting: the table.** Let W be the live draft when the run began. `answerWhileDraftWaits` (`:406`) handles the run; the rows below say what the new text does (rule, in order of how code reads them):

    | The new text | What happens | Where |
    |---|---|---|
    | Is answered by the owner's price sentence for the services W was waiting on, and W was held on price alone | The run acts as if no draft waited: the sentence goes out first, then W closes as answered (no alert) | `HeldReasons::answeredBy` `HeldReasons.php:79`; `RunFrontDesk.php:184`, `:190-192`, `:272`, `:280-282`, `closeAsAnswered` `:299`; see [message-and-verdict](../objects/messages/message-and-verdict.md) |
    | `touches_waiting` exactly false, and the words pass every check | The words send beside W; W stays live; no new alert | `RunFrontDesk.php:408`, `:430-431` |
    | Touches W, or the model could not say (null) | The words never send. They are held as `touches_waiting` and become the one fresh draft that replaces W | `RunFrontDesk.php:408-409`, `:460` |
    | A booking draft waits and the reply is not a faq answer or an intake question | Held as `waiting_guard:<label>`; Jev is not asked | `RunFrontDesk.php:336-339`, `DecideSendOrDraft.php:78` |
    | Touches W and also asks something easy | The easy part is checked on its own with the guard; if it passes, its words ride in the same text as the sentences and the fixed line, and the touching reply is the fresh draft | `RunFrontDesk.php:230-248`, `AgentReply::easyPart` `AgentReply.php:91`, `withEasyWords` `RunFrontDesk.php:610` |
    | Is marked not touching W but its words are held anyway | The agent is asked once more for one reply that covers both questions; that reply is the draft that replaces W, stored under the first reply's hold reason; if the second call fails or answers nothing the draft is W's words, a blank line and the first words | `RunFrontDesk.php:449-458`, `coverBothDraft` `:494`, `FrontDeskPrompt.php:109`, `:269` |
    | The second call of that run | It shares the first call's time budget, 150 seconds for both | `RunFrontDeskAgent.php:46`, `:57`, `:95-98`; `AgentRun.php:21` |
    | Is a check-in (the customer asks whether anyone has seen it) | W stays live and the model's words are dropped (words held for a reason of their own still replace W, but the draft keeps W's words); the owner's check-in line goes with any sentences; the owner gets a `check_in` alert once that text is out | `RunFrontDesk.php:187`, `:408-416`, `:444-446`, `:580-599` |

13. **The one fixed line.** A waiting customer is never left with no reply. The run sends one owner-written line, chosen in this order (`RunFrontDesk.php:387-389`, dispatched at `:466-474`): the complaint reply when the words were a complaint (it leads the text, D-36); the check-in reply (`sendCheckInReply`, `:580`); the partial holding line when an answer rides (`sendPartialHolding`, `:661`); the added-info reply when the customer only added a detail to a question the owner holds (`sendAddedInfoReply`, `:637`); or a new holding reply, only when the owner's own text already ended the wait. `holdingAlreadySent` is what tells the last two apart (`SendFixedReply.php:118`). The words come from `rules/replies.md` through `FixedReplies`, with every time worked out at the moment of sending (`FixedReplies.php:23-76`, `:102-112`).
14. **Alert.** `RaiseOwnerAlert::handle` stores an `owner_alerts` row per recipient, due now if urgent or the shop is open, else at the next opening (`RaiseOwnerAlert.php:39`); `SendDueAlerts` sends them (`routes/console.php:17`). A held draft alerts after it is stored, as a complaint when its reason says so, and a replacement draft alerts only if urgency rose (`RunFrontDesk.php:1059-1061`, `:1079-1095`, `:1102-1107`; a whole-thread draft is a complaint when either reply was, `:503`, `:547`). A text that closes W as answered raises no alert (`:295-297`). The check-in alert (`AlertReason::CheckIn`, `AlertReason.php:18`) follows only a text that went out (`RunFrontDesk.php:598`, `:434-436`) and the folder's right_away list (`RaiseOwnerAlert.php:86`). Owner alerts have no card yet: it comes with Phase 02.2's map (Ian, 2026-10-12).

## If you change this
**Hits:** all four object cards above, plus [conversation-and-pause](../objects/conversations/conversation-and-pause.md) at steps 2, 6 and 11 to 13. Reordering steps 6 or 8 changes what is stored when a reply is held. Moving the pick (step 9) after the decision (step 10) changes whether sentences ride with held words. A new inbound channel must go through `RecordInbound` and `DispatchInbound`, not around them. The waiting-draft table (step 12) is read back by the owner's thread, which warns when the customer wrote again since a draft (`ConversationThread.php:161`).
**Does not hit:** web form leads: they enter through the same `RecordInbound` but stop at `ProcessInbound.php:95` and reach the owner through the dashboard and `open-leads.md` (D-41; Ian, 2026-10-12: they stay a "does not hit"). A form whose words describe a danger first raises an urgent life-safety alert to the owner (`ProcessInbound.php:93`, `:122-129`) and still gets no text. The owner's own reply (`SendOwnerReply`, a separate caller of `OutboundSender`). The SDK's `agent_conversations` memory (the thread is passed in by `FrontDeskPrompt.php:139`). Booking (Phase 3).

## Surfaces
Triggered by: Twilio calling `webhooks/text/twilio` and `/status` (`routes/web.php:22,26`), once the number is live; a client's site form posting to `leads` (`routes/web.php:30`); both intended consumers, not live, since the text channel is still the fake one and nothing posts to leads (Ian, 2026-10-12).

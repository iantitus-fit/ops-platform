# Answer an inbound text

**Type:** process · **Mark:** live · **Checked:** 2026-10-18 @ 1324f24 · **Where:** `app/Actions/RecordInbound.php:49` to `app/Actions/RunFrontDesk.php:159`

**One sentence.** A customer's text is recorded, claimed once with any texts sent just after it, read once by Jev for a danger, a complaint or a request for a person, answered by the agent, judged by the send rule, and then either sent as one reply (the owner's own price or offer sentences, the model's words, or both) or kept as a draft for the owner, with the customer always getting a line back and a second check at the sender that no automated text skips.

**Input, movement, output.** Input: one inbound text from a provider webhook. Movement: record, claim, read, ask the agent, pick the owner's sentences, decide, send or hold. Output: a `messages` row for the text, usually one row for the answer (sent, or a draft with its verdict), sometimes a second automated text beside a draft, maybe intake answers, a pause, and owner alerts, some of them about the whole business rather than one customer.

**Why this shape.** Each stage is guarded by a database claim, not a queue promise, so a retried webhook, a failed-open debounce and the sweep can never answer one text twice (Phase 2 D-42, `ClaimInboundBurst.php:12-20`). The agent has no tools: it only proposes words, a label and a few flags, and code decides whether anything goes out (`FrontDeskAgent.php:15-19`). Prices and offers are the owner's own sentences, picked and sent by code without asking Jev about the words, because the model only names the service (D-04). Danger has three nets, so no one of them is the only guard: the keywords, Jev's reading of the customer's text, and the agent's own `possible_danger`. The danger text skips the wait on purpose (Phase 2 D-17). Two chokepoints hold the line for everything else: the run reads the customer's text before it acts on anything (step 7), and the sender refuses any automated text that has no reading attached (step 19).

## Steps
1. **Record.** The webhook calls `RecordInbound::handle` (`TwilioTextWebhookController.php:24`, `FakeTextWebhookController.php:21`). One transaction finds or makes the contact, finds or opens the conversation, stores the text as `received` and writes a timeline entry (`RecordInbound.php:127-184`). A text the provider already delivered returns the stored row (`:51-57`). STOP, START and HELP end here (`:76-81`; see [contact-opt-out](../objects/contacts/contact-opt-out.md)).
2. **Keyword safety line.** A text whose words describe gas, fire or water danger queues `RespondToLifeSafety` at once (`RecordInbound.php:109-121`, `RespondToLifeSafety.php:54`). `SendLifeSafetyLine` sends the fixed line, pauses and alerts (`SendLifeSafetyLine.php:63`, the send at `:100`, the pause and the alert at `:119-120`). A safety line that fails, with any error, still pauses and alerts the owner, with the reason (`:113-120`); so does a wait for the send lock that runs out (`gate.life_safety.lock_wait_seconds`, `:68-75`, `config/gate.php:142`); a retry that finds the line already sent sends no second one but finishes the pause and the alert if no alert is on file for that text (`finishHandOff`, `SendLifeSafetyLine.php:89-92`, `:133-146`); so does `RespondToLifeSafety` failing for good (`failed()`, `RespondToLifeSafety.php:72-88`, with its own `$timeout` of 120 seconds at `:39`; the alert says "could not be sent" or, when the line did go out, "sent, but check the conversation was paused"). `RunFrontDesk::handle` takes a second look before anything else, for a text the job never reached (`answerDanger`, `RunFrontDesk.php:163`, `:1225-1234`); a text already answered is skipped inside `SendLifeSafetyLine`.
3. **Queue once.** `DispatchInbound::handle` flips `dispatched_at` with a conditional update and only then queues `ProcessInbound` (`DispatchInbound.php:32-53`). A push that fails gives the claim back, setting `dispatched_at` to null, and rethrows, so the provider's retry or the sweep queues the text later (`:49-52`); the push is not deferred with `afterCommit()`, so a caller's transaction cannot move it outside that `try` (WR-04). `SweepUndispatched` re-sends texts recorded but never queued, aged 2 minutes to 24 hours (`SweepUndispatched.php:25-38`, scheduled `routes/console.php:15`).
4. **Wait for the burst.** `ProcessInbound` waits about 20 seconds after the last text, 90 at most (`ProcessInbound.php:32`).
5. **Claim.** `ClaimInboundBurst::handle` sets `handled_at` on each unclaimed customer text, one atomic update per row (`ClaimInboundBurst.php:22-39`). Nothing claimed: stop. No SMS text in the burst: stop (`ProcessInbound.php:95`). No live folder version yet: the burst is claimed and left quietly (`:101-102`). Any other error inside the run is logged, then a note and an owner alert are written through `ReportFrontDeskFailure` (`:103-107`); a run that times out or whose worker dies does the same from `failed()` (`:142-165`, `$failOnTimeout` at `:50`), reporting the newest claimed SMS text at or before the one that queued the job (WR-03). `ReportFrontDeskFailure` skips a text it already reported, so the owner hears once per text (`ReportFrontDeskFailure.php:33-40`). The burst stays claimed in every case, so the customer cannot get two replies.
6. **Opt-out stop.** `RunFrontDesk::handle` re-reads the contact; a customer who texted STOP, or whom the carrier reported as opted out, is never read and never answered. The owner is alerted to the newest text so they can call, and the run ends (`RunFrontDesk.php:165-169`, `alertAboutOptedOutBurst` `:1287-1290`). No reading is made for them: the reading comes after this stop (see [contact-opt-out](../objects/contacts/contact-opt-out.md)).
7. **The reading (one Jev call per run).** `ReadCustomerText::handle` asks Jev the owner's triage questions about the burst's words alone, with an empty draft (`ReadCustomerText.php:31`, called at `RunFrontDesk.php:171-172`). One call, a short timeout, no retry. What the run acts on is only what Jev read in the customer's own words: a complaint, a danger, a request for a person, and an unsure request for a person (`CustomerReading::complaint` `CustomerReading.php:129`, `lifeSafety` `:137`, `asksForPerson` `:145`, `unsureAboutPerson` `:153`); its price, promise and discount answers are recorded and never acted on (`:8-10`). The result is held in memory for this run only (`RunFrontDesk.php:154`, `:161`) and stored on every verdict and fixed reply as `gate.customer_reading` (see [message-and-verdict](../objects/messages/message-and-verdict.md)). It is also stored on the safety line when Jev's reading or a words check sends it (trigger `classifier`): the four classifier calls pass the run's reading as the fourth argument and `SendLifeSafetyLine` keeps it as `gate.customer_reading` beside `gate.life_safety`, so each 911 line records why it went out (`SendLifeSafetyLine.php:63`, `:104-110`; G-02.1-3). The keyword line and the agent-triggered line carry no reading and are unchanged. Two ways to have no answer, kept apart: a **failed** reading, where the call went wrong, marks Jev down (`ReadCustomerText.php:41-48`, `CustomerReading::failed` `CustomerReading.php:62`), and a **missing** reading, where no business folder is live so there are no questions to ask, is not a Jev failure and changes no status (`ReadCustomerText.php:34-37`, `CustomerReading::missing` `CustomerReading.php:71`). Both hold the model's words and the owner's sentences (`gaveNoAnswer`, `:112`). A missing reading raises `safety_check_missing` to the owner at once, at any hour (`alertAboutMissingReading`, `RunFrontDesk.php:173`, `:1257-1266`). When the reading itself finds a danger, the safety line goes out before anything else below, unless a line already answers this burst (`RunFrontDesk.php:175-177`, `safetyLineAlreadySent` `:1274-1277`).
8. **Paused and capped paths.** A paused conversation sends nothing and asks no agent (`RunFrontDesk.php:179-184`). First the reading's alerts: a complaint, and a request for a person from the reading or from the keywords, each alert goes through `RaiseOwnerAlert` on the folder's own `owner_alert` timing and neither is dropped (`alertAboutReading`, `:1413-1422`); then the one "new message while you are handling it" alert for the burst, skipped when the newest text already has an alert (`alertAboutPausedBurst`, `:1299-1306`). 9. **The person check.** Plain words that cannot mean anything else (`AsksForPerson::inText`, `AsksForPerson.php:41`), or Jev's reading of a request for a person, hand the customer to the owner before the agent is asked (`RunFrontDesk.php:194-198`). `handOffToOwner` raises the asked-for-person alert, sends the fixed handoff reply (`SendFixedReply::handoff`, `SendFixedReply.php:91`), and pauses; the text goes before the pause because the sender refuses automated texts once paused. The crash path in `ProcessInbound` stays alert-only, so a crash never risks a double text. The model is told the time now in the business's zone, in a Right now section last in its instructions (`FrontDeskPrompt.php:114`, `:293-299`), and each earlier text in the thread starts with its send time in brackets (`FrontDeskPrompt.php:140`, `:166`, `:305-310`); both are built at `RunFrontDeskAgent.php:53-54`. When a draft waits, the instructions also carry an Already with the owner section, which quotes the customer's own words that draft answered, never the draft (`FrontDeskPrompt.php:106-108`, `:234-263`). The burst it answers carries no time, because the same words also go to Jev and to the asks-for-a-person check (`FrontDeskPrompt.php:192-195`, `RunFrontDesk.php:171`, `:194`). Besides the words and the label, the model fills seven proposal fields: the services whose price was asked, whether a discount was asked, and, only when a question waits, whether the text touches it, a check-in or added-info note, and an easy part to answer alone, plus `possible_danger` (`FrontDeskAgent.php:56-74`, read by `AgentReply.php:81-87`). 11. **The third net, and the agent's own handoff.** If the agent says the text may describe a danger (`possible_danger`, told to answer true whenever it is unsure, `FrontDeskPrompt.php:63`), the safety line goes out for the burst's newest text before anything else, unless one already did (`RunFrontDesk.php:220-223`). 18. **The one fixed line.** A waiting customer is never left with no reply. The run sends one owner-written line, chosen in this order (`RunFrontDesk.php:600-613`): the complaint reply when the words were a complaint and none went out in this wait yet (at most once per wait, `complaintReplyAlreadySent` `SendFixedReply.php:161`; it goes alone, without the owner's sentences, D-36, D-43; `sendPartialHolding` `RunFrontDesk.php:1000-1025`); a later complaint in the same wait falls through to the next line, so a check-in that is also a complaint gets the check-in reply and raises only the complaint alert, never a check-in alert too: one customer text raises one alert, the more serious one (G-02.1-1, `alertsOwner` `:608`); the check-in reply (`sendCheckInReply`, `:888`); the partial holding line when an answer rides (`:1000`); the added-info reply when the customer only added a detail to a question the owner holds (`sendAddedInfoReply`, `:947`); or a new holding reply, only when the owner's own text already ended the wait. `holdingAlreadySent` is what tells the last two apart (`SendFixedReply.php:137`); a wait is not ended by a draft closed as answered unless a newer text carrying `meta.answered_by` closed it (WR-01, `answeredAfter`, `SendFixedReply.php:212-219`). The words come from `rules/replies.md` through `FixedReplies`, with every time worked out at the moment of sending (`FixedReplies.php:23-76`, `:102-112`).
19. **The second chokepoint, at the sender.** Every automated text goes through `OutboundSender::send`, whatever wrote it, and an automated text goes out only with a reading of the customer's text attached to its gate (`OutboundSender.php:39-43`, `deliver` `:203-205`, `refuseWithoutReading` `:327-342`). What each kind of text needs from the reading is `whyReadingBlocks` (`:349-370`, D-49): owner sentences need a reading that ran, did not fail and found no complaint (`CustomerReading::allowsOwnerSentences`, `CustomerReading.php:121`); the model's words need their own words check to have passed and a reading that ran and did not fail (`whyModelWordsAreBlocked`, `OutboundSender.php:409-428`); a fixed line needs only the reading record (`partsOf`, `:384-400`); a kind only a combined text has (code answer, partial holding, check-in or added-info reply) that arrives without `meta.parts` needs what both owner sentences and model words need, so a path that forgets its parts is refused (`:397`, IN-10). A reading marked missing counts as none (`readingOf`, `:435-440`). A refused send is never sent and the owner is told about the newest customer text: no reading at all raises `safety_check_missing`, right away and once per text, and a part missing what it needs raises `front_desk_failed` on the folder's timing (`:335-339`, `alertAboutRefusal` `:447-459`). The safety line (origin `LifeSafety`) and the owner's own sends are never asked for a reading (`:203`).
20. **Outage mode.** The safety check can be down for a stretch, and the owner is told without being spammed. A failed live call, whether the run's reading (`ReadCustomerText.php:46`) or a words check (`DecideSendOrDraft.php:172`), or a failed health ping marks Jev down by opening an outage; any usable answer closes it (`SafetyCheckStatus::recordFailure` `SafetyCheckStatus.php:65-80`, `recordSuccess` `:87-110`; `isDown` `:56`). The health ping is `PingSafetyCheck`, which asks Jev one fixed fictional question every five minutes, so the owner learns of an outage even on a night with no texts (`PingSafetyCheck.php:35-56`, scheduled `routes/console.php:21`; with no folder live it asks nothing and changes nothing). The owner gets one down alert per outage, never more than one per hour however often Jev flaps (`ALERT_GAP_MINUTES`, `SafetyCheckStatus.php:43`, `:173-178`), and one back-up alert when an outage whose down alert went out ends, naming how many customer texts arrived meanwhile (`backUpWords` `:161-168`). Each alert is claimed on the outage with one conditional write before its text goes out, and the claim is released when no text reached the owner, so a slow text never doubles an alert and a failed one is tried again on the next failure or answer (`claimThenSend` `SafetyCheckStatus.php:122`, IN-11). These are business-wide alerts with no conversation: `RaiseOwnerAlert::forBusiness` (`RaiseOwnerAlert.php:91-116`), `safety_check_down`, always urgent and sent right away at any hour (`isUrgent`, `:127-140`). Being marked down changes no call: every run still reads and checks. A failed reading holds the model's words and the owner's sentences, so the customer gets the owner's holding reply and the draft is pre-filled (steps 14 to 16).

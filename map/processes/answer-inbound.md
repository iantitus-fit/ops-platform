# Answer an inbound text

**Type:** process · **Mark:** live · **Checked:** 2026-10-12 @ 04f95e7 · **Where:** `app/Actions/RecordInbound.php:49` to `app/Actions/RunFrontDesk.php:82`

**One sentence.** A customer's text is recorded, claimed once with any texts sent just after it, answered by the agent, judged by the send rule, and then either sent as a reply or kept as a draft for the owner.

**Input, movement, output.** Input: one inbound text from a provider webhook. Movement: record, claim, ask the agent, decide, send or hold. Output: a `messages` row for the text, usually a second row for the answer (sent or a draft with its verdict), maybe intake answers, a pause, and owner alerts.

**Why this shape.** Each stage is guarded by a database claim, not a queue promise, so a retried webhook, a failed-open debounce and the sweep can never answer one text twice (D-42, `ClaimInboundBurst.php:12-20`). The agent has no tools: it only proposes words and a label, and code decides whether they go out (`FrontDeskAgent.php:15-19`). The danger text skips the wait on purpose (D-17).

## Steps
1. **Record.** The webhook calls `RecordInbound::handle` (`TwilioTextWebhookController.php:24`, `FakeTextWebhookController.php:21`). One transaction finds or makes the contact, finds or opens the conversation, stores the text as `received` and writes a timeline entry (`RecordInbound.php:127-184`). A text the provider already delivered returns the stored row (`:51-57`). STOP, START and HELP end here (`:76-81`; see [contact-opt-out](../objects/contacts/contact-opt-out.md)).
2. **Safety line.** A text whose words describe gas, fire or water danger queues `RespondToLifeSafety` at once (`RecordInbound.php:109-121`, `RespondToLifeSafety.php:39`). `SendLifeSafetyLine` sends the fixed line, pauses and alerts (`SendLifeSafetyLine.php:56`, the send at `:91`, the pause and the alert at `:109-110`). A safety line that fails, with any error, still pauses and alerts the owner, with the reason (`:103-110`); so does a wait for the send lock that runs out (`gate.life_safety.lock_wait_seconds`, `:61-68`, `config/gate.php:129`); so does `RespondToLifeSafety` failing for good (`failed()`, `RespondToLifeSafety.php:56-67`). `RunFrontDesk` takes a second look at step 6.
3. **Queue once.** `DispatchInbound::handle` flips `dispatched_at` with a conditional update and only then queues `ProcessInbound` (`DispatchInbound.php:28-49`). A push that fails gives the claim back, setting `dispatched_at` to null, and rethrows, so the provider's retry or the sweep queues the text later (`:45-48`). `SweepUndispatched` re-sends texts recorded but never queued, aged 2 minutes to 24 hours (`SweepUndispatched.php:25-38`, scheduled `routes/console.php:14`).
4. **Wait for the burst.** `ProcessInbound` waits about 20 seconds after the last text, 90 at most (`ProcessInbound.php:32`).
5. **Claim.** `ClaimInboundBurst::handle` sets `handled_at` on each unclaimed customer text, one atomic update per row (`ClaimInboundBurst.php:22-39`). Nothing claimed: stop. No SMS text in the burst: stop (`ProcessInbound.php:95`). No live folder version yet: the burst is claimed and left quietly (`:101-102`). Any other error inside the run is logged, then a note and an owner alert are written through `ReportFrontDeskFailure` (`:103-107`); a run that times out or whose worker dies does the same from `failed()` (`:138-157`, `$failOnTimeout` at `:50`). `ReportFrontDeskFailure` skips a text it already reported, so the owner hears once per text (`ReportFrontDeskFailure.php:33-40`). The burst stays claimed in every case, so the customer cannot get two replies.
6. **Early exits in `RunFrontDesk::handle`** (`RunFrontDesk.php:82-109`), in order: second look at danger (`:84`); opted out, so alert the owner (`:86`); paused, so alert once per burst (`:92`); reply cap reached, so pause and alert (`:98`); plain words asking for a person, so hand off: alert, fixed handoff reply, pause (`:105`, `:256-261`).
7. **Ask the agent.** `AgentFile::forChannel('sms')` (`:111`) and `RunFrontDeskAgent` try each model in file order (`RunFrontDeskAgent.php:49`; see [agent-file-and-version](../objects/folder/agent-file-and-version.md)). `RunFrontDeskAgent` starts no further fallback once the next one could not finish inside `gate.agent.chain_budget_seconds`, and never reorders the chain (`RunFrontDeskAgent.php:50-58`, `:85-88`, `config/gate.php:90`). No agent for texts, and every model failing, each write a note and alert the owner through `ReportFrontDeskFailure::handle` (`ReportFrontDeskFailure.php:31`), then stop (`RunFrontDesk.php:113-117`, `:119-125`). The agent wanting a person: hand off (`:127`).
8. **Keep what it learned.** Intake answers (`:133`, [intake-answer](../objects/intake/intake-answer.md)) and an empty contact name (`:134`) are stored before the send rule runs, even if the reply is then held.
9. **Decide.** `ComposeAutomatedText::forReply` adds disclosure and sign-off (`ComposeAutomatedText.php:26`); `DecideSendOrDraft::decide` returns the verdict (`RunFrontDesk.php:138`). A classifier-found danger sends the safety line (`:140-141`); Jev reading "asks for a person" hands off (`:143`).
10. **Send or draft.** Verdict `send`: `OutboundSender::send` (`:156`); a channel failure alerts the owner (`:166-170`), a carrier opt-out alerts the owner to call (`:172-177`), any other refusal becomes a `send_refused` draft (`:179`). Verdict `hold`: `storeDraft` withdraws any older draft, writes the new draft with its timeline entry in one transaction (`:326-365`), alerts the owner after commit (`:369-371`), and sends one holding reply unless the conversation is paused or the verdict found a danger (`:373-375`). See [message-and-verdict](../objects/messages/message-and-verdict.md).
11. **Alert.** `RaiseOwnerAlert::handle` stores an `owner_alerts` row per recipient, due now if urgent or the shop is open, else at the next opening (`RaiseOwnerAlert.php:39`); `SendDueAlerts` sends them (`routes/console.php:17`). Owner alerts have no card yet: it comes with Phase 2.1's map (Ian, 2026-10-12).

## If you change this
**Hits:** all four object cards above, plus [conversation-and-pause](../objects/conversations/conversation-and-pause.md) at steps 2, 6 and 10. Reordering steps 6 or 8 changes what is stored when a reply is held. A new inbound channel must go through `RecordInbound` and `DispatchInbound`, not around them.
**Does not hit:** web form leads: they enter through the same `RecordInbound` but stop at `ProcessInbound.php:95` and reach the owner through the dashboard and `open-leads.md` (D-41; Ian, 2026-10-12: they stay a "does not hit"). A form whose words describe a danger first raises an urgent life-safety alert to the owner (`ProcessInbound.php:93`, `:122-129`) and still gets no text. The owner's own reply (`SendOwnerReply`, a separate caller of `OutboundSender`). The SDK's `agent_conversations` memory (the thread is passed in by `FrontDeskPrompt.php:106`). Booking (Phase 3).

## Surfaces
Triggered by: Twilio calling `webhooks/text/twilio` and `/status` (`routes/web.php:22,26`), once the number is live; a client's site form posting to `leads` (`routes/web.php:30`); both intended consumers, not live, since the text channel is still the fake one and nothing posts to leads (Ian, 2026-10-12).

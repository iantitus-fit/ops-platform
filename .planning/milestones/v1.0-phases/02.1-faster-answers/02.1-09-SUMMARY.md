# Phase 02.1 Plan 09: Keyed Price Sentences and Leads Summary

**Keyed price sentences picked by code from the customer's stored intake answers, with a default sentence, one re-ask, a pending price remembered in message meta, and the owner's same, higher, lower or changed lead when an answer changes the price.**

## Performance

- **Duration:** about 8 min of commits (15:49 to 15:55 local), plus reading and closing out
- **Completed:** 2026-10-14
- **Tasks:** 3 (one tracer, two TDD)
- **Files modified:** 6 (3 app files, 2 new test files, 1 sprint log)

## Accomplishments

- A customer who asks what a new system costs is asked the size first. Code writes `price_pending` on that message, and when the answer comes, code sends the owner's sentence for that size even if the model forgot to flag the price again (D-05).
- An answer that matches no option is asked again once with the price kept pending; a second miss, or an option the owner has no sentence for such as "Not sure", sends the owner's default sentence. With no default on file the price holds as a draft naming the service (D-05, D-06).
- When an answer changes the price, the new sentence goes out right away behind the owner's lead. The lead is worked out in integer cents: identical amounts are `same`, a new range at or above the old highest is `higher`, at or below the old lowest is `lower`, and only overlapping ranges are `changed`. So `$2,000 to $5,000` followed by `$5,000 to $10,000` reads as higher (D-09, D-39).
- A correction to the same option sends nothing; asking again with no change re-sends the last sentence behind `Here's that estimate again:`; a version with no price leads sends the sentence alone.

## Decisions Made

- A pick that still needs answers, when the model wrote no words to ask them, is held like a price with no sentence and names the service. This keeps the existing "keyed service until the pick exists" test and its owner-facing reason unchanged.
- A sentence with a different key but identical amounts is sent with the `same` lead (research A6), following the plan's "with a different key, send with the lead from direction()".
- The pending list is read in PHP from the newest outbound message with `in_reply_to`, newest by sent time then id.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Newest-message lookup returned the oldest message**
- **Found during:** Task 3 (the "correction to the same option" case sent a "same" lead it should not have)
- **Issue:** `RunFrontDesk::pendingPriceSlugs()` (written in Task 1) used `lazyByIdDesc()` on `$conversation->messages()`, but that relation already sorts oldest first, so the descending id order was only a tie-break and the lookup found the first outbound message, which still said the price was pending. Task 1's two-message test could not show it.
- **Fix:** both newest-first lookups (`pendingPriceSlugs()` and `PriceSentencePicker::lastSent()`) now `reorder()` and sort by `coalesce(sent_at, created_at) desc, id desc`. `currentFor()` uses `reorder('id')` so newest-wins does not lean on the relation's order.
- **Files modified:** app/Actions/RunFrontDesk.php, app/SendRule/PriceSentencePicker.php, app/Actions/RecordIntakeAnswers.php
- **Verification:** PriceLeadTest "sends no sentence when the correction maps to the sentence already sent" and the full suite pass
- **Committed in:** 08f6c7a

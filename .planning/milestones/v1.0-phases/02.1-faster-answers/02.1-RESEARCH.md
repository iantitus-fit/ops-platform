### Price sentences (reopens Phase 2 D-08 and D-01's dollar check; Ian's explicit call)
- **D-04:** **A price goes out on its own only as an owner-written price sentence that code sends.** Each service file may carry price sentences, checked at sync against the file's prices (the Phase 2 D-12 pattern). The agent only names the service (and its label is `price`); when that service has a sentence that fits, **code** sends it and **Jev is skipped because code wrote it**. A price the model writes itself still holds exactly as Phase 2 D-08 says: D-08's floor stands for model-written replies, and price sentences are fixed replies, not an exception to it. `price_policy: none` always holds. Why: a model-written price can match a folder amount and still be wrong ("Furnace repair is $89" when $89 is the diagnostic fee), so matching amounts is not enough. — **Reversibility:** costly — the price-sentence fields become part of every client's service files and the sync contract; changing their shape means migrating owner folders.
- **D-05:** **Intake first, and the answers pick the price.** A service file can key price sentences to intake answers (for example current unit size), plus a **default sentence** for when the customer can't or won't answer. The default opens with an owner-written acknowledgement and may carry several ranges ("No problem if you're not sure what you have. A replacement system typically runs $2,000 to $5,000 installed for a smaller unit and $5,000 to $10,000 for a larger one. We'll lock in an accurate quote once we see your setup."). Like every price sentence, the default must name its service (D-08). The agent asks the keying intake questions before any price; code picks the sentence from the stored intake answers (Phase 2 D-33) and sends it. A service whose single sentence is keyed to nothing (the $89 diagnostic) sends right away. **No default sentence and no matching answer means it holds** as a price draft. The model never writes a number or the acknowledgement.
- **D-06:** **Owner-defined options.** Intake options can carry the owner's meaning ("Small (under 3 tons)", "Large (3 tons and up)") so the agent can match an answer like "about 3 tons" the first time. Each answer-keyed price sentence **names its option** ("For a larger system, 3 tons and up, ...") so a wrong match is visible to the customer. Naming the option is **README guidance, not a sync check**. An answer that matches no option is **re-asked once**, offering the options in the owner's words; still no match, the default sentence goes out, and the owner sees the raw words on the card.
- **D-07:** **Mixed reply ("How much is the diagnostic, and do you work on Carrier units?").** The reply is two parts. Code sends the price sentence; the model's non-price words always go through all three Phase 2 D-01 checks on their own, so a number the model writes still holds. Both pass: **one combined text, price sentence first**, one sign-off, one count against the reply cap (Phase 2 D-52), the Phase 2 D-50 disclosure leading it when it is the first automated text. Price sentence passes and the model's part holds: the price sentence goes out with an **owner-written partial holding reply** in the same text ("I've passed your other question to {owner_name}..."), a new entry in `rules/replies.md` checked at sync like the others; the held part becomes the draft. Why: the customer must know the unanswered part is with a person, not ignored.
- **D-08:** **No clear service.** "How much for a repair?" with two candidate services: the agent asks which system (an intake-style question that sends on its own under the normal checks), then code sends that service's sentence. The model names no service, or a slug not in the folder: it holds as a price draft with the holding reply. **Each price sentence must name its own service** ("AC repair starts with..."), so a wrong pick is visible to the customer and the correction rule (D-09) re-sends the right one. **Sync check (confirmed by Ian, 2026-10-14):** the sync refuses any price sentence, the default sentence included, that does not contain its service file's `name`, compared case-insensitively. "Both" sends both sentences in one text.
- **D-09:** **Change awareness.** Code records which price sentence went out last in the conversation. A corrected intake answer (a new row, Phase 2 D-34) that maps to a **different** sentence sends it right away; one that maps to the **same** sentence sends nothing; a correction to "not sure" sends the default sentence. The customer asking again with no change re-sends the last sentence. Each re-send carries an **owner-written lead** chosen by code from the amounts: **"same"** when nothing changed, **"higher"** when every new amount is above the old, **"lower"** when every one is below, **"changed"** when the ranges overlap. Leads live in `rules/replies.md`, checked at sync; the model never writes the comparison. Why: a customer left holding a lower number in writing loses trust when the real quote comes.
- **D-10:** **Sync checks on price sentences:** every amount must match the file's prices (its `price_cents`, or the range fields the sentence is keyed to); **no** price or discount-phrase check (the furnace file's "waived" is a discount phrase in `CodeChecks::DISCOUNT_PHRASES` and must not block the owner's own terms); the **promise** and **never_say** checks stay. The promise check is what keeps a price sentence from becoming binding ("guaranteed", "for sure" are refused at sync). Estimate wording is recommended in the folder README with an example, not enforced.
- **D-11:** Price and offer sentences follow **every existing stop**: nothing in a paused conversation (Phase 2 D-24), nothing after STOP (Phase 2 D-40), each counts against the reply cap (Phase 2 D-52). Life-safety still goes first (Phase 2 D-17).

### Offer sentences (reopens Phase 2 D-08 for discount; Ian's explicit call)
- **D-12:** **Same shape as price.** The folder lists offers; each has an owner-written **conditional** offer sentence ("If you're a first-time customer, we're running a promotion that takes $50 off your first visit"), its amount or percentage fields, a **required start date** and an **optional end date**. The business confirms eligibility at the visit. Why: a conditional offer the owner already published promises nothing new, and making every offer wait for approval brings back the delay. — **Reversibility:** costly — a new folder file type and sync contract.
- **D-13:** **Code never decides whether this customer qualifies.** It only checks the offer is **live today**: start and end dates in the business's time zone, end date inclusive. When the label is `discount` and offers are live, code sends **every live offer's sentence in one text**, and Jev is skipped. A mixed reply follows D-07's split rules.
- **D-14:** **No live offer:** the owner-written **discount holding reply** (Ian's warm deferral: "We like to take care of our customers. I'll make sure {owner_name} knows you asked about a discount and he'll pick up the thread.") goes out and the owner is alerted (Phase 2 D-14 and D-20 apply). A missing discount reply falls back to `holding_reply`.
- **D-15:** **Sync checks on offer sentences:** amounts and percentages must match the offer's fields; **no** discount-phrase check; promise and never_say stay.
- **D-16:** The **Business Folder page warns** about any offer live more than **90 days with no end date**. The warning never blocks a send. Why: a forgotten standing offer costs money on every quote, and with the owner out of the loop nobody else will notice.
- **D-17:** Phase 3's walk-test example "the agent would now quote a price" is **reworded to mean a price that is not in the folder** (ROADMAP.md updated by this discussion).

### A second question while one waits (amends Phase 2 D-28)
- **D-18:** **Touches flag.** The agent's structured output says whether the new message **touches the waiting question**. Only a **clear no** lets a passing answer send while the old draft stays live, untouched, with its alert. **Yes or blank:** today's Phase 2 D-28 path, one fresh draft covering the whole thread replaces the old one. There is still at most one live draft. Why: "Actually Friday works better" answered on its own would leave a live Thursday draft that sends the wrong day. — **Reversibility:** costly — changes the draft lifecycle every later phase builds on (02.2 reply codes, Phase 3 booking).
- **D-19:** **Split.** A message that both touches the waiting question and asks something easy ("Do you do heat pumps? Also Friday might work better") is split: the easy part may send on its own, everything touching the waiting question becomes the new draft replacing the old (Phase 2 D-28). The split-off part goes in the same text as the partial holding line (D-20).
- **D-20:** **Label guard.** While a draft waits, an answer may send only if its label is `faq_answer` or `intake_question`, **never `scheduling`**, and it still passes all three Phase 2 D-01 checks (Jev's intent bar is the second look at a mixed reply). The guard applies **on a split**, and **whenever the waiting draft's own label is `scheduling`** (code reads it from the stored verdict, Phase 2 D-07), regardless of the touches flag. Otherwise every `send_on_own` label can send, scheduling included: a booking reply goes out while a price or discount question waits. Why: holding booking behind an unrelated question slows the step that finishes the conversation, and the label floor keeps the model from committing to a day while one is with the owner.
- **D-21:** **A price draft solved by a sentence.** When a waiting draft held on **price alone** (from its verdict) and a price sentence now fits (the customer named the service), code sends the sentence and **closes the draft as `answered`**: a new draft resolution kept for the labeled data (Phase 2 D-07), a timeline entry saying why, no alert, and Send (or a 02.2 reply code) refused with "Already answered". If the draft also held on anything else (complaint, promise), the sentence still sends and a fresh draft replaces the old one for what remains (Phase 2 D-28), so the owner still sees it. — **Reversibility:** costly — a new `DraftResolution` value in the calibration dataset (gate:export, D-02).
- **D-22:** **Owner alert.** An answer sent while a draft waits sends **no new alert** (Phase 2 D-22 unchanged). Safety net: a waiting draft with newer customer messages shows **"The customer wrote again since this draft"** above Send.
- **D-23:** **Prompt fix:** the agent is told never to mention a question already with the owner; the holding reply covered it.

### Holding replies and the customer who waits (amends Phase 2 D-14 and D-22; keeps D-51)
- **D-24:** **Principle for this phase and after: customer-first communication.** A waiting customer is reassured until they are contacted. The wording, timing and how much is the owner's call per business, captured at onboarding (see Owner setup questions).
- **D-25:** **Phase 2 D-51 stays exactly as it is** for `{next_open}`. New fill-ins sit beside it, each computed in code from `hours.md` so it is always true: one for **"today if he can, or after we open at 8 am tomorrow"**, one for **the next opening time alone**, and an optional **check-in time**. The owner chooses which to use; the promise is not fixed for every business.
- **D-26:** **Check-in time:** an owner setting, **off by default**: a number of hours after the next opening following the hold (8 am + 2 = "10 am tomorrow"), closures skipped; a hold at 9 am on a Tuesday still gets Wednesday's time; a result after closing uses closing time. A reply that uses the check-in fill-in while the setting is off fails the sync in plain words.
- **D-27:** **The example folder's holding reply is rewritten in the customer-first voice** and promises a place in line, not a time ("I've passed this to {owner_name} and you're on his list, and he'll get back to you as soon as he can after we open..."); "answers questions like this himself" goes. Why: several overnight texts each promised "first thing" commit the owner to more than he can keep.
- **D-28:** **Check-in reply.** A customer who checks in while a draft waits ("just checking in, haven't heard back") gets the owner-written **check-in reply**, **every time**, not only the first (like the handoff reply, which `SendFixedReply` already sends every time a customer asks again), bounded by the reply cap (Phase 2 D-52). **Each check-in alerts the owner right away** (amends Phase 2 D-14 and D-22).
- **D-29:** **Added-info reply and the code guarantee.** `rules/replies.md` also gets an **"added to your question"** reply ("Got it, I've passed that along to {owner_name} with your question."). **Code guarantee:** if a customer writes while a draft waits and the run sends them nothing, code sends one of the two: the agent's structured output picks check-in or added-info, and **unsure means added-info**, so a missed detection still reassures. **Only a check-in alerts the owner**; new info updates the draft quietly per Phase 2 D-22, because under D-28 the fresh draft already covers it and the old wording can't be sent.
- **D-30:** **Partial holding line bookkeeping.** The partial holding line (D-07, D-19) goes in the same text as the answer it rides with and **counts as the holding reply for the new draft**. Implementation note: `SendFixedReply::holdingAlreadySent()` ends the wait when any real answer is sent after a holding reply, so the partial line must be recorded where that check counts it (a holding-reply kind or equivalent); otherwise a full holding reply follows as a second text. Same for a price or offer sentence sent with the partial line.
- **D-31:** **Per-reason holding replies:** **discount** gets the warm deferral (D-14; falls back to `holding_reply`), **complaint** gets its own owner-written holding reply, **required in every folder** because a complaint can arrive anywhere, checked at sync (promise and never_say apply). Price, promise and other keep `holding_reply`. More per-reason replies wait until an owner asks.
- **D-32:** **Required only where used.** The sync requires each new reply only when the folder uses the feature that sends it: the four price leads once any service has price sentences; the discount reply is optional (falls back); the **partial holding, check-in, added-info and complaint** replies are **always required**, because the code guarantee, splits and complaints can send them in any folder. The sync names what is missing in plain words. — **Reversibility:** costly — new required fields in `rules/replies.md` for every client folder.
- **D-34:** **Reply priority (confirmed by Ian, 2026-10-14).** When a new message holds for its own reason while another draft waits (for example a complaint), **one fixed reply goes out per run**, chosen in this order: life-safety, then handoff, then the complaint holding reply, then check-in, then added-info.

## Summary

Phase 02.1 is a send-path and sync-contract phase with no new libraries and no new external API. The work falls into four connected pieces. (1) A new owner-written content family, price sentences on service files and offer sentences on a new `offer` file type, validated at sync against the numbers in their own fields and sent by code through the same path as the existing holding and handoff replies (`SendFixedReply` pattern: queued, then sent, Jev skipped, `gate.fixed = true`). (2) A restructured `RunFrontDesk` that, when a draft is already waiting, decides per run whether the new message touches that draft, splits off an easy part, or only needs to be reassured, and always sends the customer exactly one owner-written text. (3) New fill-ins computed in `BusinessClock` and new required fields in `rules/replies.md`. (4) Small UI and bookkeeping edges: the `answered` draft resolution with "Already answered", "The customer wrote again since this draft", the offer-over-90-days warning, and a new owner-alert reason for check-ins.

No migration is needed. Every new value lives in a plain `string` column (`messages.kind`, `messages.resolution`) or inside the existing `messages.meta` / `messages.gate` JSON, and the folder contract lives in the compiled `icm_versions.compiled` JSON. That sidesteps the SQLite partial-index rebuild trap on `messages_one_live_draft_per_conversation` entirely (STATE.md 02-19); if a task nevertheless adds a foreign-key column to `messages` or `conversations`, it must drop and recreate that index afterwards, exactly as `2026_10_12_000008_add_pause_columns_to_conversations_table.php` does.

Four traps in the existing code will silently defeat the decisions if the plans do not name them: `SendFixedReply::holdingAlreadySent()` ends a wait on any outbound text that is not a `HoldingReply` (so the new reply kinds, and an easy answer sent while a draft waits, would each cause a second full holding reply); the example voice file's `never_say` contains `no problem`, which is the first words of the default sentence quoted in CONTEXT; the owner's own discount reply contains the word "discount", which `CodeChecks` vetoes; and `Validator::REPLY_FILL_INS` is also spelled out in an error message that an existing test asserts verbatim. All four are verified below.

**Primary recommendation:** Build bottom-up and test-first in this order: (a) enums, kinds and the `holdingAlreadySent()` rewrite; (b) sync contract (service price sentences, `offer` type, new replies, amount helper) with the example folder updated in the same plan; (c) fill-ins; (d) `PriceSentencePicker`, offer-liveness and the code-answer send action; (e) `AgentReply` / schema / prompt fields; (f) the `RunFrontDesk` decision table, `answered` close and check-in alert; (g) UI edges; (h) docs, map cards and the sprint walk-through log. Keep the model's structured output strictly a proposal: price and offer sentences are chosen and sent by code from stored intake answers and the clock, never from model text.

### Pattern 1: A code-written answer is a fixed reply (reuse the existing path)

**What:** Price and offer sentences, the partial holding line, check-in, added-info, complaint and discount replies are all text written by the owner, checked at sync, and sent by code without Jev. Send them exactly the way `SendFixedReply::holding()` and `handoff()` do: compose with `ComposeAutomatedText::forReply` (disclosure first when it is the first automated text, sign-off last), then `OutboundSender::send(..., SendOrigin::Automated, [...])` with `gate_outcome => Send`, `gate_reason => 'fixed_reply'` and a `gate` JSON that says `fixed: true`.

**When to use:** every text in this phase that code, not the model, wrote.

**Evidence:** `SendFixedReply::holding()` builds `['kind' => MessageKind::HoldingReply, 'gate_outcome' => GateOutcome::Send, 'gate_reason' => 'fixed_reply', 'gate' => ['version' => 1, 'fixed' => true, 'reason' => ['code' => 'fixed_reply', 'plain' => null]]]`. [VERIFIED: app/Actions/SendFixedReply.php:47-52]

Rules that must hold for every one of these sends (they are already enforced by the one outbound path, so keep the new code *after* the early exits in `RunFrontDesk::handle`, never before):

- Paused conversation: refused for `SendOrigin::Automated` (`OutboundSender::whyBlocked()`), and `RunFrontDesk` never reaches the agent while paused. STOP: refused for every origin. [VERIFIED: app/Actions/OutboundSender.php whyBlocked(); RunFrontDesk.php:86-96]
- Reply cap: `replyCapReached()` counts every outbound `Agent` text with status queued, sent or delivered except `LifeSafety`, so the new kinds count automatically (D-11, Phase 2 D-52). [VERIFIED: RunFrontDesk.php:237-247] One text per run keeps the cap honest.
- Danger first: a keyword hazard sends the safety line and pauses the conversation inside `answerDanger()`, so the later `isPaused()` early exit stops every sentence. A hazard Jev finds on the model's words (`verdict->lifeSafety`) must also stop code answers for that run; handle it before sending sentences. [VERIFIED: RunFrontDesk.php:84-96, 140-142]
- `activity_summary` is an `OutboundSender` attribute that words the timeline entry (e.g. "Price sentence sent by front desk"); it is stripped before the insert. [VERIFIED: OutboundSender.php deliver(): `$summary = $attributes['activity_summary'] ?? null; unset(...)`]

### Pattern 2: The sentence contract (front matter) and its sync checks

All field names below are **provisional** (CONTEXT lists them as Claude's Discretion). They are the shape this research recommends; the planner should freeze them in the first plan and write them into `docs/SPEC.md`.

**Service file** (`type: service`), new optional fields:

```yaml
price_sentences:                       # optional list; each entry is one owner sentence
  - answers: {unit_size: "Small (under 3 tons)"}   # optional map: intake key => exact option. Absent = unkeyed (sends right away)
    sentence: "For a smaller system, under 3 tons, a replacement system typically runs $2,000 to $5,000 installed."
    amounts_cents: [200000, 500000]    # every dollar amount in the sentence, as cents
price_default:                         # optional; used when the customer can't or won't answer
  sentence: "That's fine if you're not sure what you have. A replacement system typically runs $2,000 to $5,000 installed for a smaller unit and $5,000 to $10,000 for a larger one. We'll lock in an accurate quote once we see your setup."
  amounts_cents: [200000, 500000, 500000, 1000000]
```

Sync checks (all plain-words, naming file and field; the existing `PlainWords::label()` already renders `price_sentences.0.sentence` as "price_sentences item 1: sentence"):

1. **Amounts match, both directions.** The set of dollar amounts found in `sentence` (as integer cents) must equal the set in `amounts_cents`. For an unkeyed sentence on a service, `amounts_cents` may be omitted and defaults to `[price_cents]`. A declared amount missing from the text is also an error (stops stale fields). (D-10)
2. **Name check.** `sentence`, and `price_default.sentence`, must contain the service file's `name`, compared case-insensitively on squished whitespace. (D-08, confirmed by Ian)
3. **Promise and never_say only.** Run `CodeChecks::findings($text, $neverSay)` and keep only findings whose `rule` is `promise` or `never_say`. Skip `price` (amounts are checked in step 1 instead) and `discount` (D-10, D-15). `never_say` comes from the voice file in the same candidate folder, never `ActiveConfig`, exactly as `Validator::repliesErrors()` already does. [VERIFIED: Validator.php repliesErrors() docblock and body]
4. **Bare numbers.** A plain number within three words of a price word (the existing `numberNearPriceWord` finding, `rule: price`, whose match has no `$`) is an error: "write each amount with a $ sign". Without this, `costs 4000` would pass step 1 with an empty amount set.
5. **`price_policy: none` + any price sentence is an error** ("furnace-tune-up has price_policy none, so you quote it yourself; remove the price sentences"). (D-04: `price_policy: none` always holds.)
6. **Keys and options.** Each `answers` key must be one of the service's `intake.*.key`; each value must equal one of that question's `options`; no two sentences may have the same `answers`; all keyed sentences must use the same set of keys (keeps picking unambiguous).
7. **Fill-ins:** sentences take none (`{...}` is an error). Keeps them literally what the owner wrote.

**Offer file** (new `type: offer`, one fact one file, e.g. `business/offers/first-visit-promotion.md`):

```yaml
---
type: offer
name: First visit promotion
slug: first-visit-promotion
sentence: "If you're a first-time customer, we're running a promotion that takes $50 off your first visit."
amount_cents: 5000        # exactly one of amount_cents / percent
start_date: 2026-10-01    # required, Y-m-d
end_date: 2026-12-31      # optional, Y-m-d, on or after start_date
---
```

Checks: required fields; exactly one of `amount_cents` / `percent` (1 to 100); dollar amounts in `sentence` equal `[amount_cents]` (or percent: every `N%` / `N percent` equals `percent`); promise and never_say only; `end_date >= start_date`; duplicate slug (extend `duplicateSlugErrors()` beyond `service`). Registering the type needs `Loader::TYPED` (`['business', 'hours', ..., 'set_replies', 'triage']`) to gain `'offer'`, and `FolderSync::compile()` to index offers by slug; today an unlisted type falls into `default => $compiled['index'][$file->type] = $file->path`, which would make offers a singleton and silently keep only the last file. [VERIFIED: app/Icm/Loader.php:23; app/Icm/FolderSync.php:210-227]

**`rules/replies.md`** (`type: set_replies`), new fields:

```yaml
partial_holding_reply: "I've passed your other question to {owner_name}, and he'll follow up on it."   # always required (D-32)
check_in_reply: "..."                    # always required
added_info_reply: "Got it, I've passed that along to {owner_name} with your question."   # always required
complaint_reply: "..."                   # always required, every folder (D-31)
discount_reply: "We like to take care of our customers. I'll make sure {owner_name} knows you asked about a discount and he'll pick up the thread."   # optional; falls back to holding_reply (D-14)
price_leads: {same: "...", higher: "...", lower: "...", changed: "..."}   # required once any service has price sentences (D-32)
check_in_hours: 2                        # optional integer 1 to 12; absent = check-in time OFF (D-26)
```

Required-where-used is a cross-file check, so it goes in `repliesErrors()` (which already receives all files), not in `rulesFor()`. Missing field wording follows the existing style: "rules/replies.md: partial_holding_reply is missing, and it is required". For the leads add which service made them necessary. Every reply field gets the same treatment `REPLY_FIELDS` gives `holding_reply` today: unknown fill-in, then the code checks on the text with `{...}` stripped.

- `Validator::REPLY_FILL_INS` and the sentence in `repliesErrors()` (`'; the only fill-ins are {owner_name}, {business_name} and {next_open}'`) both list the fill-ins. Build the sentence from the constant, and update `tests/Feature/Icm/RepliesValidationTest.php` row `'a fill-in nobody knows'`, which asserts that exact string. [VERIFIED: Validator.php:50, 728; RepliesValidationTest.php:16]
- `{check_in_time}` in any reply while `check_in_hours` is absent: "partial_holding_reply uses {check_in_time}, but check_in_hours is not set; set it or take the fill-in out" (D-26).
- `discount_reply` skips only the `discount` code rule (it must say "discount"); `price_leads.*` and every other reply keep `price`, `discount`, `promise`, `never_say`. See Pitfall 3.

Recommended new fill-ins (names provisional): `{today_or_next_open}` ("today if he can, or after we open at 8 am tomorrow"), `{next_opening}` ("8 am tomorrow"), `{check_in_time}` ("10 am tomorrow"). `{next_open}` keeps its meaning byte for byte (D-25).

### Pattern 3: `PriceSentencePicker` (deterministic, from stored rows)

Inputs: conversation, service slug, the live service file (via `ActiveConfig::service()`), the conversation's *current* intake answers, and the last sent price sentence for that service. Output: one of `Send(sentenceKey, text, amounts)`, `NeedsAnswers(keys)`, `Hold(reason)`.

Algorithm:

1. Service unknown, `price_policy: none`, or no price sentences and no default: `Hold('no sentence')` (D-04, D-08). Do not trust the slug beyond `ActiveConfig::service($slug) !== null`.
2. **Current answers** = highest `id` per (conversation, service, question): the same rule `CustomerCard::intakeAnswerLines()` uses (`->orderBy('id')` then `keyBy('question_key')`); write it once as a helper beside `RecordIntakeAnswers` and reuse. [VERIFIED: app/Actions/RecordIntakeAnswers.php docblock; app/Records/CustomerCard.php intakeAnswerLines()]
3. **Unkeyed sentence** (no `answers`): send right away (the $89 diagnostic).
4. **Keying questions** = the keys named in `answers`. A keying question with no row yet: `NeedsAnswers` (the model's own next intake question goes out normally, and code remembers the price is pending, below).
5. Keyed match: a sentence whose `answers` all equal the current options wins.
6. No match: if every keying question has a row and the row has an `option` (a real option nothing is keyed on, e.g. an owner-listed "Not sure"): the default sentence (D-05). If a keying row has `option = null` (stored as unmatched with raw words): count rows with null option for that question. **One** null: `NeedsAnswers` once so the model re-asks offering the options in the owner's words (D-06); **two or more**: the default sentence, and the owner sees the raw words on the card (already shown as "not matched" with the quoted raw text by `CustomerCard`). No default: `Hold`.
7. **Change awareness (D-09).** Look at the most recent sent message in the conversation whose `meta.price_sentences` mentions this service (read the last few rows and decode `meta` in PHP, no JSON-path query). Compare its `sentence_key` (`default`, `unkeyed`, or `unit_size=Large (3 tons and up)`) to the pick:
   - a *new intake row for a keying question in this run* and the key is unchanged: send nothing for price;
   - key changed: send now with a lead by amounts;
   - customer asked again (`price_services` names the service) and the key is unchanged: re-send with the `same` lead.
8. **Lead by amounts** (D-09), pure integer comparison of the old and new `amounts_cents`: new.min greater than old.max is `higher`; new.max less than old.min is `lower`; identical sets is `same`; anything else is `changed`. The model never writes the comparison. [ASSUMED] that identical amount sets count as `same` even when the sentence key differs (see Open Question 5).
9. **Price pending across turns (recommended).** When the pick is `NeedsAnswers`, store `meta.price_pending = [slug, ...]` on the outbound agent message of that run (sent or draft). At the start of the next run, the newest outbound agent message's `price_pending` is merged into the model's `price_services`. This makes "asked the keying question, then gets the sentence" deterministic even if the model forgets to re-flag the price ask. [ASSUMED] design; the alternative is a prompt instruction to keep `price_services` set until a sentence has gone out, which fails silently when the model forgets.

### Pattern 4: The `RunFrontDesk` decision table (the heart of ANSR-03 / ANSR-04)

Keep every early exit of `handle()` exactly as it is (danger, opted out, paused, reply cap, phrase handoff, no agent, agent failure, `wantsPerson`). The new logic starts after `recordIntakeAnswers` / `fillEmptyName` (current lines 133-134). Let **W** be the conversation's live draft (`messages.status = 'draft'`, at most one by the partial unique index), **S** the code-written parts (price and offer sentences), **R** the model's `reply` (may be empty only when it flags a price or discount ask), **E** the split-off easy part.

Steps:

1. Build **S** from `price_services` (plus pending) and `asks_discount`. No live offer and discount asked: S is empty and R must be held with reason `discount:no_live_offer` (D-14). Services flagged but unresolved: R (or a code placeholder draft body when R is empty) held with reason `price:no_sentence`.
2. If R is non-empty run `DecideSendOrDraft::decide()` on R exactly as today (all checks recorded, Jev only when the cheap checks pass, `lifeSafety` / `asksForPerson` acted on exactly as now).
3. If W exists and **S is non-empty and W was held on price alone** (read from W's stored verdict, Pattern 8): after S has been sent, close W as `answered`; for the rest of the run behave as if there is no W (D-21).
4. If W exists, apply D-18 to R:
   - `touches_waiting` is exactly `false` (a clear no): R may send if it passes. Apply the label guard (`faq_answer` or `intake_question` only) when E exists **or** `W->label === ReplyLabel::Scheduling` (D-20). A failing R is stored as the new draft and replaces W (D-28).
   - `touches_waiting` is `true` or missing/malformed: R never sends. Convert a sending verdict with `$verdict->heldFor('touches_waiting')` (the same trick `RunFrontDesk` already uses for `classifier:life_safety` at line 142); a verdict that already holds keeps its own, more specific reason. The result is stored as the new draft and replaces W.
   - `waiting_note = check_in` (and no new content): W stays untouched, no new draft, R is discarded (D-28).
5. If E (the easy part) exists, run `decide()` on E with the label guard; its words send (inside the combined text) only when all three checks pass. Jev reads the whole burst and may hold E on intent; that is by design (D-20 "Jev's intent bar is the second look at a mixed reply").
6. Compose **one** text: S sentences first, then the words that passed (R when sendable, else E), then at most one fixed line, then sign-off, with the disclosure leading if it is the first automated text (D-07, D-50). Check the total against `SendOwnerReply::MAX_LENGTH` (1,600) before sending; if too long, send S alone and hold the model part. The fixed line, in priority order (D-34, with partial holding as the line that rides an answer):
   - a draft was stored for a complaint reason: `complaint_reply`;
   - `waiting_note = check_in`: `check_in_reply` and `RaiseOwnerAlert(CheckIn)`;
   - a draft was stored (replacing W or a first draft) *and* an answer part (S or E) is in the text: `partial_holding_reply`; that text is stored with `kind = partial_holding` so it counts as the holding reply (D-30);
   - a draft replaced W and nothing else is being sent: `added_info_reply` (also the default when `waiting_note` is missing or unrecognised: "unsure means added-info", D-29);
   - a first draft with nothing else sent: today's `holding()` (reason-specific wording: complaint, discount, else `holding_reply`).
   The combinations of check-in or complaint *with* an answer part are not spelled out in CONTEXT; the above is a recommendation (Assumption A5). `storeDraft()` must stop calling `holding()` unconditionally; the holding decision becomes the caller's.
7. A run that sends nothing to a customer who wrote while W waited is impossible by construction: either R/E/S sent, or one fixed line sent (D-29 code guarantee). Write that as a test that loops over every branch.
8. Alerts: unchanged for drafts (`ownerNeedsAlertFor`, D-22). Sending S/R/E while W waits raises no alert (D-22). Only a check-in alerts (always urgent, Pattern 9).

### Pattern 5: Message kinds, `holdingAlreadySent()` and the partial line (D-30)

`holdingAlreadySent()` today finds the newest `kind = holding_reply`, then says the wait ended if any later outbound sent/delivered text has `kind` null or `!= holding_reply`, or any draft with resolution approved/edited/discarded was resolved after that holding reply was created. [VERIFIED: app/Actions/SendFixedReply.php:94-123, lines 97, 112, 116]

Consequences if the plans only add kinds:

- A partial holding line stored under a new kind is not found as "latest holding" (line 97) so a full holding reply follows as a second text (the trap CONTEXT names).
- Any check-in or added-info reply counts as a "real answer" (line 112) and ends the wait, so the next replacement draft sends a full holding reply again.
- An easy answer sent while W waits (D-18) is also an outbound text with `kind` null / `agent_reply`, so it too ends the wait although W is still live.

Recommended rewrite:

- `MessageKind` gains (names provisional): `PartialHolding = 'partial_holding'`, `ComplaintHolding = 'complaint_holding'`, `DiscountHolding = 'discount_holding'`, `CheckInReply = 'check_in_reply'`, `AddedInfoReply = 'added_info_reply'`, `CodeAnswer = 'code_answer'` (a text carrying price/offer sentences without a partial line). Add `startsWait()` returning `[HoldingReply, PartialHolding, ComplaintHolding, DiscountHolding]` and use it in the "latest" lookup.
- Clause 1 of "answered since" becomes: an outbound message after the latest one, sent or delivered, **authored by the owner** (`MessageAuthor::Owner`). Automated texts sent while a draft waits must not end the wait; automated texts sent when no draft waits cannot occur without the draft having been resolved, which clause 2 already covers.
- Clause 2 adds `DraftResolution::Answered` to `[Approved, Edited, Discarded]`.
- Update `tests/Pest.php` helpers `textsSentForAgentReplies()` and `theAgentMessage()`, which exclude only `HoldingReply` and `LifeSafety` by kind (lines 207 and 223); a new-kind text would otherwise be counted as "the agent's own words" and `->sole()` would throw. [VERIFIED: tests/Pest.php:207, 223]
- Existing tests that will legitimately change because a second customer text now gets a reply: `HoldingReplyTest` ("sends no second holding reply when a newer text replaces the waiting draft" asserts one text to Dana in total), parts of `DraftReplacementTest`, `HeldDraftTest`, `ReplyCapTest`, `SentTimeTest`. Update them deliberately, test-first; do not loosen them to pass.

Note the exact current literal in `HoldingReplyTest`: `"Thanks! Mike answers questions like this himself. I've sent him your message, and he'll get back to you when we open at 8 am tomorrow."` D-27 rewrites that holding reply in the example folder, so that expectation changes with it. [VERIFIED: tests/Feature/FrontDesk/HoldingReplyTest.php; examples/example-hvac/rules/replies.md]

### Anti-Patterns to Avoid

- **Letting the model choose or paraphrase a price sentence.** The model supplies only service slugs and intake answers. A sentence the model rewrites is a model-written price and must still hold (D-04).
- **Adding a `touches` rule that lets a passing reply send and leaves a stale draft live without the flag.** With `touches_waiting` true or missing, a reply that would pass must still become the replacing draft (Pattern 4 step 4), or "Actually Friday works better" sends while a Thursday draft stays live.
- **Calling `holding()` from `storeDraft()` unconditionally.** After this phase the caller decides which single fixed line goes out.
- **Closing W as `answered` before the sentence is sent.** Send, then close.
- **JSON-path SQL on `meta` / `gate`.** Different on SQLite and PostgreSQL; decode in PHP.
- **Editing the example voice file's `never_say` to make a sample sentence pass.** Existing tests rely on `no problem` being in that list (RepliesValidationTest uses it twice). Reword the sentence.
- **A migration that adds a foreign key to `messages` or `conversations`** without recreating `messages_one_live_draft_per_conversation` (and, for `conversations`, `conversations_one_open_per_contact`).
- **Treating a README as a validated file.** `Loader::load()` skips every `README.md`; the router files (`CLAUDE.md`, `CONTEXT.md`, `START-HERE.md`) are fingerprinted and can mint a version. [VERIFIED: Loader.php:37, 60-62]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Sending a code-written text | A second send path | `OutboundSender::send` through `SendFixedReply`-style methods | Lock, pause, STOP, 1,600-char guard, queued-then-sent bookkeeping, failure recording are all already there |
| Disclosure and sign-off | String concatenation | `ComposeAutomatedText::forReply` | First-automated-text logic (D-50) already correct, including a failed first send |
| Plain-words sync errors | New message formatter | `PlainWords::render` / `PlainWords::oneLine` and `Validator::error()` | Shape of `changelog.md` lines and the exact-string tests depend on it |
| Code checks on owner text | A new regex set | `CodeChecks::findings()` filtered by `rule`, plus two small public helpers added to `CodeChecks` | One hard-veto list, shown to the owner on the Business Folder page |
| Business-hours arithmetic | Raw `Carbon` day math | `BusinessClock` (`nextOpening`, `windowOn`, `timeWords`, `dayWords`) | DST, closures and the 14-day look-ahead are already handled and tested |
| Owner alerts | Direct SMS to the owner | `RaiseOwnerAlert::handle` | Dedupe, urgent/after-hours timing, failed-alert visibility |
| Draft end bookkeeping | Deleting or copying a draft | The `discard()` pattern: lock row, set status Withdrawn plus resolution | Drafts are never deleted (labeled data, D-54) |
| Current intake answer | New table or column | Highest `id` per (conversation, service, question) over `intake_answers` | Already how the card and Phase 3 read it (Phase 2 D-34) |
| Date comparison for offers | Timestamp math | `Y-m-d` string comparison in the business zone (`CarbonImmutable::now($tz)->toDateString()`) | Lexicographic order equals date order; avoids DST and signed `diffInDays` |

**Key insight:** every hard part of this phase is already solved once for the holding and handoff replies. The risk is not missing machinery, it is the several places that assume "the only automated, non-answer text is a `HoldingReply`".

## Common Pitfalls

### Pitfall 1: The CONTEXT default sentence fails the example folder's own `never_say`
**What goes wrong:** CONTEXT's sample default sentence begins "No problem if you're not sure what you have." The example voice file says `never_say: [guaranteed, cheapest, no problem]`, and D-10 keeps the `never_say` check on price sentences, so the example folder would be rejected at sync. Probe run this session: `CodeChecks::findings()` on that sentence returned `[{"rule":"price","match":"$2,000"},{"rule":"never_say","match":"No problem"}]` (the `price` finding is the one D-10 skips; `never_say` is the one that blocks). [VERIFIED: examples/example-hvac/voice/how-we-talk.md:5 `never_say: [guaranteed, cheapest, no problem]`; probe output; CONTEXT.md D-05, line 167]
**How to avoid:** the example folder's sentence must say something else ("That's fine if you're not sure what you have."), which the same probe passed. Do not touch the voice file.
**Warning signs:** the first `icm:sync` of the updated example folder is rejected with `uses a phrase the voice file says never to use (No problem)`.

### Pitfall 2: `waive` / `discount` phrases and "$50 off" in owner sentences
**What goes wrong:** applying `CodeChecks::findings()` unfiltered to a price or offer sentence rejects the owner's own terms. Probe: the $89 diagnostic sentence "we waive the $89" returns `{"rule":"discount","match":"waive"}`; the offer "takes $50 off your first visit" returns `{"rule":"discount","match":"$50 off"}` and a `price` finding for `$50`. [VERIFIED: probe output; CodeChecks.php:25, `DISCOUNT_AMOUNT_PATTERNS`]
**How to avoid:** keep only `promise` and `never_say` findings (D-10, D-15), and verify amounts with the dedicated helper.

### Pitfall 3: The owner's discount reply contains the word "discount"
**What goes wrong:** D-14's warm deferral says "asked about a discount". Probe: `CodeChecks::findings()` returns `{"rule":"discount","match":"discount"}`. With the same loop that checks `holding_reply` today, the sync would reject the example folder's `discount_reply`. CONTEXT only names the price/offer exemption (D-10, D-15), not this reply. [VERIFIED: probe output]
**How to avoid:** for `discount_reply` skip only the `discount` rule; keep `price`, `promise`, `never_say`. The other new replies keep all four rules.

### Pitfall 4: `holdingAlreadySent()` ends the wait on the wrong texts
See Pattern 5. Three separate failures: the partial line is not "the latest holding", check-in and added-info count as answers, and an easy answer sent while W waits counts as an answer. Cover all three with tests before changing `RunFrontDesk`.

### Pitfall 5: SQLite rebuild drops `messages_one_live_draft_per_conversation`
Not triggered if no migration touches `messages` (this research needs none). If one is added: Laravel rebuilds a SQLite table when a foreign-key column is added and keeps a partial unique index only as a plain one, which would then refuse the second row of any status. Drop and recreate it after the change, as `2026_10_12_000008_add_pause_columns_to_conversations_table.php` does for `conversations_one_open_per_contact`. The index SQL is `create unique index messages_one_live_draft_per_conversation on messages (conversation_id) where status = 'draft'`. [VERIFIED: migrations 2026_10_12_000006 and 2026_10_12_000008; STATE.md 02-19]

### Pitfall 6: Example folder growth moves file-count assertions
`exampleFolderFileCount()` returns `12` today (profile, hours, lead sources, faq, three services, voice, sending, replies, triage, agent). Adding a replacement service file and one offer file makes it 14. The literal `expect(exampleFolderFileCount())->toBe(12)` at `tests/Feature/SendRule/JevClassifierTest.php:64` and the helper at `tests/Pest.php:252` both change; the many tests that call the helper follow it. `business/services/CONTEXT.md` lists services by name and should list the new one (it is a router, so editing it mints a version, which is fine). [VERIFIED: tests/Pest.php:252, JevClassifierTest.php:64, examples/example-hvac/business/services/CONTEXT.md]

### Pitfall 7: Time-dependent example data
The example offer needs real dates. A test that asserts "offer is live" will start failing on the real calendar once `end_date` passes, and the 90-day warning will start appearing for an open-ended offer. Pin the clock with `$this->travelTo(Carbon::parse('2026-10-13 10:00', 'America/Chicago'))`, as `HoldingReplyTest` already does. YAML detail: an unquoted `2026-10-01` becomes a `DateTime` that `Loader::plainValues` turns into the string `2026-10-01`; quoted dates stay strings; `hours.md` closures use quoted dates. Both work. Closures in the example hours: `closures: ["2026-11-26", "2026-12-25"]`. [VERIFIED: Loader.php:149-158; examples/example-hvac/business/hours.md]

### Pitfall 8: Exhaustive `match` expressions
`CustomerCard::section()` matches every `ActivityType`; `AlertReason::plainWords()` matches every case. Adding a case without its arm throws `UnhandledMatchError` at render time (card render runs in a queued listener and in every prompt). Add the arms in the same commit as the cases. [VERIFIED: CustomerCard.php:155-169; AlertReason.php plainWords()]

### Pitfall 9: Jev only reads the model's words
A pure price or discount ask has no model words, so Jev is not asked, which means Jev's `life_safety` and `asks_for_person` readings do not run for that text. Keyword danger (`LifeSafety::hazardIn`), the phrase handoff (`AsksForPerson::inText`) and the model's own `wants_person` all run earlier and still stop the run. This matches D-04 ("Jev is skipped because code wrote it") and is an accepted gap. For a mixed reply Jev reads the whole burst, so "How much is the diagnostic, and do you work on Carrier units?" can legitimately score a price-question intent and hold the model's part; the sentence still goes out with the partial holding line (D-07). [VERIFIED: DecideSendOrDraft.php:75-83; RunFrontDesk.php:84-109]

### Pitfall 10: A replaced draft hides the old question (D-18 / D-28 tension)
With `touches_waiting = false` and a reply that is itself held, the new draft must still replace W (one live draft). The prompt told the model not to mention W's question, so the owner's new draft no longer shows it. See Open Question 1.

### Pitfall 11: Old active version, new code
A version that went live before this phase has no `partial_holding_reply` etc., and the new validator will reject the unchanged folder at the next sync, so the old version stays live while new code runs. Runtime readers of the new keys must tolerate their absence (fall back to `holding_reply`; treat no offers and no price sentences as none) until the owner syncs a fixed folder. `ActiveConfig::services()` and `->service()` already read `compiled['index']['service'] ?? []` style; do the same for `offer`. No client is live yet (STATE.md: ZDR route required "before a real client goes live"), so this only matters for dev databases. [CITED: STATE.md Blockers/Concerns]

### Pitfall 12: Combined text over 1,600 characters
`OutboundSender::whyBodyIsRefused()` refuses more than 1,600 characters, and the draft path turns a non-`NOT_SENT` refusal into a `send_refused` hold. Several offers plus a long default sentence plus model words plus disclosure plus sign-off can exceed it. Measure the composed text; drop the model part to a draft before the sentences. [VERIFIED: OutboundSender.php whyBodyIsRefused(), RunFrontDesk.php:165-179]

### Pitfall 13: Double sends and races
Three existing guards cover most of it: the burst claim (`handled_at` conditional update), the `Cache::lock("reply:{conversation}")` in `OutboundSender`, and `lockForUpdate` on the draft row. Keep the answered-close inside a transaction with a status re-check, and keep "pick the sentence" idempotent (re-running with the same rows gives the same key), so a retried job cannot send two different sentences.

### Dollar amounts as integer cents (new public helper on `CodeChecks`)
```php
/**
 * Every dollar amount in a text as integer cents, in no particular order, without floats.
 * "$2,000" is 200000; "$89.50" is 8950; "120 dollars" is 12000.
 *
 * @return list<int>
 */
public static function dollarAmountsInCents(string $text): array
{
    $found = [];

    preg_match_all('/\$\s?(\d+(?:,\d{3})*)(?:\.(\d{1,2}))?/u', $text, $symbol, PREG_SET_ORDER);
    preg_match_all('/(?<![\p{L}\p{N}_$])(\d+(?:,\d{3})*)(?:\.(\d{1,2}))?\s+(?:dollars?|bucks?)(?![\p{L}\p{N}_])/iu', $text, $word, PREG_SET_ORDER);

    foreach ([...$symbol, ...$word] as $match) {
        $found[] = ((int) str_replace(',', '', $match[1])) * 100 + (int) str_pad($match[2] ?? '0', 2, '0');
    }

    return array_values(array_unique($found));
}
```

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt injection through a quoted waiting question | Tampering | Quote through the same cleaning as alerts, label it information not instructions, keep the model tool-less (`FrontDeskAgent` declares no tools) |
| Model names the wrong service or invents a slug | Tampering | Slug must resolve via `ActiveConfig`; every sentence names its own service so the customer can see a wrong pick (D-08) |
| Owner-written sentence becomes a binding promise or a wrong number | Repudiation / Tampering | Sync checks: amounts equal declared fields, promise and never_say still apply, estimate wording in README |
| Code-written text bypasses Jev | Elevation of privilege | Skip only for text that passed the sync checks and is read from the compiled copy; model words in a mixed reply still go through all three checks (D-07) |
| Alert injection through customer words in a check-in alert | Spoofing | `OwnerAlertText::clean()` already swaps links, emails and long digit runs; keep the dashboard link added last by us |
| Duplicate or contradictory price texts from a retried job | Tampering / DoS | Burst claim, send lock, deterministic pick, answered-close in a transaction |
| Reply loops between auto-responders | DoS | Reply cap counts every new kind; one text per run |

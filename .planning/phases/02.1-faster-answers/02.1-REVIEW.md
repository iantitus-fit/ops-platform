# Phase 02.1: Code Review Report

**Reviewed:** 2026-10-14
**Depth:** standard
**Files Reviewed:** 83
**Status:** issues_found

## Summary

I read all 31 application and view files in full, the example folder, the map cards and the SPEC and sprint diffs, and scanned the tests for assertions that cannot fail, missing clock pins and missing cases. Three claims were checked by running throw-away Pest probes (since deleted; the working tree holds nothing new) and by calling `CodeChecks` directly.

What held up:
- The hard parts that were easiest to get wrong are sound: integer cents are used throughout, with no float on the money path (`CodeChecks::dollarAmountsInCents`, `PriceSentencePicker::amounts`, `Validator::dollars`).
- The new queries use `coalesce(...)` and plain bindings, so SQLite and PostgreSQL behave the same.
- The `ActiveConfig` binding is scoped, so a queue worker does not serve a stale price sentence after a sync.
- The offer date window, the end-date-inclusive rule and the day-90 versus day-91 warning are right.
- `closeAsAnswered` takes a row lock and re-checks the status, so the owner's approval and a code close cannot both win.
- Every model-written word still goes through label, code and Jev, except in the paths below.

The two critical findings are the same shape. The phase made "code wrote it" a reason to skip Jev, and two paths now act on a customer text that no check has read: a complaint can be answered with a price sentence and no alert, and a draft can be closed as "price alone" on a hold that never read the customer's words. The warnings are one decision-level regression (D-30), two veto and sync gaps, one lifecycle gap, and test gaps that explain why the suite did not catch the criticals.

## Critical Issues

### CR-01: A complaint (or promise) in a price or discount text is answered with the owner's sentence and never reaches the owner

**File:** `app/Actions/RunFrontDesk.php:179-194` (the `codeOnly` branch), `app/Ai/AgentReply.php:54-56`, `app/SendRule/DecideSendOrDraft.php:96-117`
**Issue:**
- When the model returns blank words with `price_services` or `asks_discount`, `codeOnly` is true and `sendCodeAnswer()` sends the sentences. Jev is not asked, and `$run->reply->label` is not looked at at all.
- Jev is the only check that reads the customer's text for a complaint. `LifeSafety::hazardIn` covers danger keywords and `AsksForPerson` covers person phrases. Neither covers a complaint.
- Probe, run as one Pest test: the customer writes "Your tech was rude and I want to complain. How much is a repair?" and the model replies with `reply: ''`, `label: 'complaint'`, `price_services: ['ac-repair']`. Result: one `code_answer` message with the $89 sentence. There is no draft, no owner alert and no complaint reply.
- Even the model's own `complaint` label is thrown away, because the label check lives in `decide()`, which is skipped here.
- D-04 says Jev is skipped "because code wrote it". That is true of the words, but not of the customer text, and the customer text is what Jev reads for complaint.
- The same hole applies to the blank-word holds in `holdWithoutWords`: they record `classifier.ran=false`.

**Fix:** Do not let a blank-word run bypass the customer-text checks. At minimum, hold the run when the model's label is a floor label other than price or discount:
```php
// RunFrontDesk::handle(), before computing $codeOnly
$labelBlocksCodeAnswer = $words === ''
    && in_array($run->reply->label, [ReplyLabel::Complaint, ReplyLabel::Promise], true);

$codeOnly = ! $labelBlocksCodeAnswer && $words === '' && ($sentences !== [] || $checkIn) && ! $priceHeld && ! $noLiveOffer;
```
Route that case to `holdWithoutWords($run, $customerText, 'label:'.$run->reply->label->value)`. The sentences can still ride with the complaint reply through `sendPartialHolding`, which already has the complaint arm. Better: also ask Jev the triage questions about the customer text with empty agent words, hold-only, so a complaint the model mislabelled is still caught. Add a test for each path.

### CR-02: A draft held without Jev having read the customer's words is treated as "held on price alone" and auto-closed, dropping the owner's alert

**File:** `app/SendRule/HeldReasons.php:36-57` and `:153-170`; `app/SendRule/DecideSendOrDraft.php:76-88`; `app/Jobs/SendDueAlerts.php:62-72`
**Issue:**
- `priceAlone()` requires every recorded check to agree. A check that did not run counts as agreeing: `($checks['length']['passed'] ?? null) !== false` is true for null, and `readingIsPriceAlone(null)` returns true.
- A reply with `label: price` is vetoed at the label check, so Jev never runs and `checks.classifier.reading` is null. `holdWithoutWords` also leaves the classifier unrun. A complaint, promise or discount request in the customer's words is therefore invisible, yet the draft reads as price alone.
- Probe, after hours (6 pm, shop closed): the customer writes "Your tech was rude last time and I am furious. How much for a new unit?" and the model replies "Mike will text you a price." with label `price`. Result: draft W is held, with a `draft_waiting` alert due at 8 am. The customer then writes "It's the AC" and the model names `ac-repair` with `touches_waiting: true`. The sentence is sent and W is closed as `answered` with no alert. The next morning `SendDueAlerts` skips the W alert as "Handled before it was due".
- The owner never hears about the complaint, and the customer only got a price sentence.
- The unit tests for `priceAlone` only feed it hand-built gate arrays, and the "price and a complaint" test depends on the model choosing a label that lets Jev run, so neither exercises the vetoed path.

**Fix:** Close only on evidence, not on the absence of a failed check. Require that Jev actually read the customer text:
```php
$reading = $checks['classifier']['reading'] ?? null;
if (($checks['classifier']['ran'] ?? false) !== true || ! is_array($reading)) {
    return false; // nobody read the customer's words, so a price sentence cannot be said to finish this draft
}
```
That makes the blank-word `price:no_sentence` drafts unclosable. So also have `holdWithoutWords` and the label-veto path ask Jev about the customer's text (hold-only, as in CR-01) and record the reading. Then `priceAlone` has something to check. Add a test that runs the vetoed path end to end: a complaint in the customer text, label `price`, then a sentence, and assert W stays live.

## Warnings

### WR-01: The D-30 trap is still there for the "price sentence closes W, rest becomes a new draft" path

**File:** `app/Actions/RunFrontDesk.php:280-283`; `app/Actions/SendFixedReply.php:130-144`; `map/processes/answer-inbound.md` (step 13); `map/objects/messages/message-and-verdict.md` ("Which kinds start a wait")
**Issue:**
- `sendPartialHolding()` runs first, creating the partial holding message M. `closeAsAnswered()` then stamps W with `resolved_at` at or after `M.created_at`.
- `holdingAlreadySent()` takes M as the newest wait-starting message and counts any `Answered` resolution with `resolved_at >= M.created_at` as "the owner answered since". So the new draft X, which M is meant to cover (D-30), reads as having no holding reply.
- Probe: customer writes, W is held on price and gets a holding reply. A second text names the service and asks something else, which the model holds with a promise. Result: the sentence plus partial line go out (message 5), W is `answered`, and X is a draft. A third text "Hello?" then gets a second full `holding_reply` (message 9) instead of the added-info line.
- The customer receives holding, partial line, then holding again. The map's own statement that "a customer who texts again ... gets no second holding reply" is false on this path.

**Fix:** Do not let a close made by the partial line count as ending the wait it rides with. In the `Answered` arm of `holdingAlreadySent()`, compare the answering message to the latest wait-starter, in PHP so it is portable:
```php
$answered = $conversation->messages()->where('resolution', DraftResolution::Answered)
    ->where('resolved_at', '>=', $latest->created_at)->get()
    ->contains(fn (Message $draft) => ($draft->meta['answered_by'] ?? 0) > $latest->id);
```
Then add a regression test that sends a third text after the close-plus-partial path and asserts the kind is `added_info_reply`.

### WR-02: The send-rule price veto does not catch amounts spelled in words

**File:** `app/SendRule/CodeChecks.php:18`, `:59-62`, `:41`
**Issue:**
- The veto catches only `$` plus digits, "N dollars" or "N bucks", and a bare digit string within three words of a price word.
- Direct call result: "A new unit runs about five thousand dollars installed.", "Expect to pay around five grand.", "It is around 5k for that." and "Repairs run eighty-nine bucks." all return `[]` (no finding). Only "$89" is caught.
- `MONEY_WORDS` and `moneyWordIn()` exist in the same class, but only the sync uses them. For model-written words the protection is therefore the model's own label plus Jev's price bar. D-02 says the code veto is a floor no model can overrule, and this part of the floor is open.

**Fix:** Add a rule to `findings()` that treats a money word or k-shorthand as a price, ideally tied to proximity, so "thousands of customers" does not hold:
```php
$price = self::earliest($text, self::PRICE_AMOUNT_PATTERNS) ?? self::numberNearPriceWord($text) ?? self::moneyWordNearPriceWord($text);
```
`moneyWordNearPriceWord()` would reuse the three-word window with `MONEY_WORDS` and the `5k` pattern. Add unit cases for each phrase above.

### WR-03: A sync-checked price or offer sentence can still carry an unchecked amount (D-37 not fully met)

**File:** `app/Icm/Validator.php:1152-1202` (`priceSentenceError`), `:894-943` (`offerSentenceError`), `app/SendRule/CodeChecks.php:166-172`
**Issue:**
- D-37 says one checked amount must not let an unchecked one ride along, and the docblock calls the sync "the only check it ever gets". The sync compares `$` amounts and rejects a fixed word list, but these pass:
  - "AC repair starts at $89 plus eighty more per hour." (no money word listed)
  - "AC repair is $89, or 120$ after hours." (dollar sign after the digits)
  - "AC repair starts at $89 plus 150 for parts, a typical fee." (the bare number is five words from "fee", outside the window)
- Each returns no money word, no bare number and `dollarAmountsInCents` of only `[8900]`, so each equals the declared 8900 and the file is accepted.
- The owner wrote these, but the stated purpose of the check is to stop an unchecked figure being sent without anyone reading it.

**Fix:** In `priceSentenceError` and `offerSentenceError`, refuse any digit run that is not part of a `$` amount, a percentage, or the service name:
```php
$stripped = preg_replace(['/\$\s?\d[\d,]*(?:\.\d+)?/u', '/\d+(?:\.\d+)?\s?(?:%|percent)/iu'], ' ', str_ireplace($name, ' ', $sentence));
if (preg_match('/\d/', $stripped) === 1) { /* "write every amount with a $ sign" */ }
```
Add number words (twenty, thirty and so on, half, double) to a second list. This is a fail-closed check, so a clear message to the owner is needed.

### WR-04: A blank-words price or discount answer sends beside a waiting draft without regard to `touches_waiting`

**File:** `app/Actions/RunFrontDesk.php:188-197`, `:414-419`
**Issue:**
- With a draft waiting and blank model words (the normal shape for a sentence-only answer), `$verdict` is null. `answerWhileDraftWaits` then sends the sentence and returns, whatever the model said about touching W.
- Example: W is a scheduling draft for Thursday, and the customer writes "Actually Friday works better. Any discounts?". The offer sentence goes out. W is not replaced, so the draft still says Thursday, and the Needs-you card shows only the "The customer wrote again" badge. This is exactly the stale-Thursday case D-18 was written to prevent.
- The test "a blank reply leaves the draft live" asserts this on purpose. That is an acceptable fallback for a text that does not touch W, but not for `touches_waiting === true`.

**Fix:** When `$words === ''`, `$stillWaiting !== null`, `touchesWaiting !== false` and the text is not a check-in or an answer that closes W, still send the sentences but raise the whole-thread draft: reuse `coverBoth` (second agent call, `coverBoth: true`) or at least store a fresh draft for the thread. At the least, mark the live draft `needs review` so 02.2's reply code can refuse it. Add a test for the Friday case.

### WR-05: `unmatchedCount()` counts every miss in the history, not the current run of misses

**File:** `app/SendRule/PriceSentencePicker.php:199`, `:231-238`
**Issue:**
- The docblock says "earlier misses do not matter once the newest answer matches". The query does not do that: it counts all rows with `option` null for the service and question.
- Sequence: a miss (count 1, asked again), then a match ("Small"), then later a new miss from a correction such as "not sure what I said earlier". The count is now 2, so the picker sends the default sentence with no re-ask.
- D-06 says "re-asked once", and the intake card says the same. The result is a different price sentence than the owner designed for that customer.

**Fix:** Count only the trailing run of misses after the newest matched row:
```php
$lastMatch = $conversation->intakeAnswers()->where('service_slug', $slug)->where('question_key', $key)->whereNotNull('option')->max('id') ?? 0;
return $conversation->intakeAnswers()->where(...)->whereNull('option')->where('id', '>', $lastMatch)->count();
```

### WR-06: A check-in draft stores the waiting body under the check-in words' verdict

**File:** `app/Actions/RunFrontDesk.php:444-460`
**Issue:**
- When a check-in's words are held for a reason of their own, `$draftWords = $waiting->body` but `$verdict` is the verdict of the check-in words. `storeDraft()` writes both onto one row.
- So the stored `label`, `gate_reason` and `gate.inputs.agent_reply` describe text that is not the row's body. D-07 and `gate:export` treat the pair as labeled calibration data, so these rows will be mislabeled in the dataset.
- The mismatch also feeds `HeldReasons::priceAlone` on this row. The replacement chain is checked too, so I found no unsafe close, but the row reads as a verdict for words it does not hold.

**Fix:** Store W's own gate for the kept body and record the check-in words' verdict under a meta key (as `first_reply` does on the whole-thread draft):
```php
$attributes['meta'] = [...$attributes['meta'], 'check_in_reply_gate' => $verdict->details];
$verdict = Verdict::fromStored($waiting); // or copy $waiting->gate / gate_reason / gate_outcome
```

### WR-07: No test covers the paths behind CR-01, CR-02 and WR-01, and one test hides a branch in its assertion

**File:** `tests/Feature/FrontDesk/AnsweredDraftTest.php:377-397`, `tests/Feature/FrontDesk/OfferSentenceTest.php:134-149`, `tests/Feature/FrontDesk/PriceSentenceTest.php:286-300`
**Issue:**
- Missing cases:
  - A blank-word price or discount ask whose label is `complaint` or `promise`.
  - A complaint in the customer text with the reply labelled `price`, then closed as answered (the "price and a complaint" test only works because the model picked a label that lets Jev run).
  - A follow-up text after the close-plus-partial-line path (WR-01).
  - A blank-word reply with `touches_waiting: true` and a waiting scheduling draft (WR-04).
- `AnsweredDraftTest.php:396` asserts `$reply === '' ? $live->id === $waiting->id : $live->id !== $waiting->id` inside `expect(...)->toBeTrue()`. The two cases are different tests wearing one name, and a failure message says only "true expected, false given".
- Several data-driven tests branch with `if (...) { expect(...); return; }` so each row reads a different assertion; this works but hides which expectation a failing row broke.

**Fix:** Add the four tests above, and split the conditional ones into two `it()` blocks or two datasets with the expected value as a dataset column.

## Info

### IN-01: A check-in line sent with sentences is recorded as a `code_answer`

**File:** `app/SendRule/ReplyParts.php:42-51`, `app/Actions/SendCombinedReply.php:75-83`
**Issue:** `kind()` returns `CodeAnswer` when sentences are present and the line is a check-in or added-info line, so the timeline says "Owner's price or offer sentence sent" and the `check_in_reply` kind is not recorded. `meta.parts` still lists `check_in_line`. Nothing breaks today, but anything that later keys on kind (the 02.2 follow-up, the export) will miss it.
**Fix:** Put the check-in and added-info line kinds ahead of `CodeAnswer` in the `match`, or record both in meta.

### IN-02: "Held: no price on file" is shown for a service that only needs the customer's answers

**File:** `app/Actions/RunFrontDesk.php:204`
**Issue:** The reason names every `NEEDS_ANSWERS` slug as "no price on file". For the replacement system, which has sentences, this tells the owner something untrue. It happens when the model returns blank words and no question for a service that still needs an answer (the prompt asks it to write the question).
**Fix:** Name only `HOLD` slugs in the sentence. For `NEEDS_ANSWERS` slugs use "waiting on the customer's answers for X", or re-ask the agent.

### IN-03: A failed partial-holding send drops the owner's sentence without telling the owner

**File:** `app/Actions/RunFrontDesk.php:677-685`
**Issue:** If `sendCombinedReply->handle` throws, the catch calls `report()` and sends the plain holding reply. The price or offer sentence the customer asked for is lost, the owner sees an ordinary draft alert, and nothing records that the sentence did not go out. In the D-21 branch the waiting draft is also not closed.
**Fix:** Add a timeline note ("Price sentence could not be sent") or raise `FrontDeskFailed` for the failed send, as `sendCodeAnswer` does.

### IN-04: `pendingPriceSlugs()` reads the newest outbound row of any status

**File:** `app/Actions/RunFrontDesk.php:726-739`
**Issue:** The query has no status filter, so a failed send, a withdrawn draft or the empty `send_refused` draft (which writes `price_pending => []`, `:816`) can supply or erase the pending list. The consequence is small, since the customer is simply asked again, but the intent was "what the previous run left".
**Fix:** Filter to `Queued`, `Sent`, `Delivered` and `Draft`, or write the pending list from the failed path.

### IN-05: `RunFrontDesk` is one 1,100-line class with a 175-line `handle()` and a 14-argument private method

**File:** `app/Actions/RunFrontDesk.php:115-292`, `:406`; also `:90` and `:338`
**Issue:** `handle()` interleaves price picking, offers, label guards, life safety, easy parts and sending, and `answerWhileDraftWaits` takes 14 parameters. The label list `[FaqAnswer, IntakeQuestion]` is written twice (`SPLIT_LABELS` and inside `labelGuardFor`). The map cites 40 line numbers into it, so every edit makes the map stale.
**Fix:** Pull the waiting-draft branch into its own class that takes a small value object, reuse `SPLIT_LABELS` in `labelGuardFor`, and cite function names in the map instead of line numbers.

### IN-06: The services README says the service name must appear "exactly" but the sync compares case-insensitively

**File:** `examples/example-hvac/business/services/README.md` (section "Say the service's name every time"), `app/Icm/Validator.php:1184`
**Issue:** "exactly as it is in the file" is stricter than the check (case-insensitive, whitespace squished). An owner may waste time matching case, or conclude "ac repair" is refused.
**Fix:** Say "the service's name, in any capitals".

### IN-07: The customer's words are placed in the model's instructions

**File:** `app/Ai/FrontDeskPrompt.php:233-262`
**Issue:** "Already with the owner" quotes the customer's earlier texts in the instruction channel (up to 300 characters each). They are cleaned of links and numbers and whitespace-collapsed, so a text cannot start a new heading, and the section marks them as information. The system-level channel still carries stranger-written text that the thread would carry in a user turn. T-02.1-10 considered this; I record it so it stays a deliberate choice.
**Fix:** If the model supports it, put the quoted texts in the user turn, or label each quote with a delimiter the cleaner strips from customer text.

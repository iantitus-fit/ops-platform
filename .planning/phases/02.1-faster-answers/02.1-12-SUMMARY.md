# Phase 02.1 Plan 12: Answers While a Draft Waits Summary

**While a draft waits for the owner, an easy answer marked touches_waiting false sends on its own beside it, anything touching it becomes the one fresh draft, a scheduling answer is blocked by a recorded label guard, and every waiting customer gets exactly one owner-written line by priority, with check-ins alerting the owner on the folder's right_away timing.**

- **Tasks:** 3
- **Files modified:** 7 (2 created, 5 modified)

## Accomplishments

- `RunFrontDesk` has a waiting-draft branch: a reply with `touches_waiting` exactly false and all three checks passing sends beside the live draft (no alert, draft untouched); null, missing or true takes the replace path, held as `touches_waiting` (D-18, D-22).
- `DecideSendOrDraft::decide()` takes an optional label list; the guard and its result are stored on `checks.label` (`guard`, `guard_passed`) and a failure holds as `waiting_guard:<label>` after the label check and before length, so Jev is never asked. `RunFrontDesk` applies `[faq_answer, intake_question]` only when the waiting draft's stored label is scheduling (D-20).
- One owner-written line per run in the order complaint, check-in, partial holding (an answer rides), added-info, then a fresh holding reply when the owner's own text already ended the wait (D-34, D-36). A complaint line leads the text; the others follow the answer.
- A check-in gets the check-in reply every time (bounded by the reply cap) and raises a `check_in` alert on the customer's newest text; the alert's timing is the owner's right_away list (D-28, D-38). A check-in's words never send beside the waiting draft and never become the body of the draft that replaces it.
- An every-branch test proves a customer who writes while a draft waits gets exactly one new text, at most one live draft exists, and the text holds at most one fixed line.

## Decisions Made

See `key-decisions` above. In short: a check-in's `label:other` or guard hold is dropped like a sending check-in; a fresh draft that keeps W's body keeps W's label too; a blank reply with nothing to say is still held, not silent; the check_in alert follows a text that actually went out.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A check-in labeled `other` replaced the waiting draft**
- **Found during:** Task 3 (first GREEN run)
- **Issue:** The plan's own check-in example is labeled `other`, which fails the send_on_own list (`label:other`) and so would count as "held for a reason of its own" under row 3, replacing W. The plan's expectation is that W stays live.
- **Fix:** For a check-in, a hold from the guard or from a label that is not in `ReplyLabel::neverOnItsOwn()` (the owner simply did not list it for sending) is dropped, like a check-in whose words would send. Holds for price, promise, discount, complaint, code checks, Jev or length still go to row 6.

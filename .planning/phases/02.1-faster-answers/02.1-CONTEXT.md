# Phase 02.1: Faster Answers - Context

**Gathered:** 2026-10-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Take the owner out of routine questions so the customer conversation finishes faster. Delivers: owner-written **price sentences** per service, picked by code from the customer's intake answers and sent without the owner; owner-written **offer sentences** sent while an offer is live; an easy answer that **no longer waits behind a hard question** already with the owner; a waiting customer who **always hears back** (partial holding line, check-in reply, added-info reply, complaint and discount holding replies); new **time fill-ins** for the holding reply computed from `hours.md`; and the prompt fix so the agent never mentions a question already with the owner.

Requirements: ANSR-01, ANSR-02, ANSR-03, ANSR-04 (added to REQUIREMENTS.md by this discussion).

**Scope swap (decided this discussion, Ian, 2026-10-14):** this phase was inserted as the Owner Loop. It becomes **Faster Answers**, and the Owner Loop moves unchanged to **Phase 02.2** with its own discuss later. Why: the fastest to finish the conversation gets the business, so remove the owner from routine questions first, then make the owner fast when they are needed.

Not in this phase: everything on the 02.2 Owner Loop list (staff users and the approve switch, reply codes, email alerts and the "handled" follow-up, re-alerts and the backup recipient, the customer update past the promise, assist mode, the on-call switch, the fallback classifier, the Phase 2 review carry-overs including WR-09); scheduling inside the text thread and moving bookings (Phase 3); recalibrating the `asks_for_person` unsure band.

</domain>

### Price sentences (reopens Phase 2 D-08 and D-01's dollar check; Ian's explicit call)
- **D-04:** **A price goes out on its own only as an owner-written price sentence that code sends.** Each service file may carry price sentences, checked at sync against the file's prices (the Phase 2 D-12 pattern). The agent only names the service (and its label is `price`); when that service has a sentence that fits, **code** sends it and **Jev is skipped because code wrote it**. A price the model writes itself still holds exactly as Phase 2 D-08 says: D-08's floor stands for model-written replies, and price sentences are fixed replies, not an exception to it. `price_policy: none` always holds. Why: a model-written price can match a folder amount and still be wrong ("Furnace repair is $89" when $89 is the diagnostic fee), so matching amounts is not enough. — **Reversibility:** costly — the price-sentence fields become part of every client's service files and the sync contract; changing their shape means migrating owner folders.
- **D-05:** **Intake first, and the answers pick the price.** A service file can key price sentences to intake answers (for example current unit size), plus a **default sentence** for when the customer can't or won't answer. The default opens with an owner-written acknowledgement and may carry several ranges ("No problem if you're not sure what you have. Smaller units typically run $2,000 to $5,000 installed, larger ones $5,000 to $10,000. We'll lock in an accurate quote once we see your setup."). The agent asks the keying intake questions before any price; code picks the sentence from the stored intake answers (Phase 2 D-33) and sends it. A service whose single sentence is keyed to nothing (the $89 diagnostic) sends right away. **No default sentence and no matching answer means it holds** as a price draft. The model never writes a number or the acknowledgement.
- **D-06:** **Owner-defined options.** Intake options can carry the owner's meaning ("Small (under 3 tons)", "Large (3 tons and up)") so the agent can match an answer like "about 3 tons" the first time. Each answer-keyed price sentence **names its option** ("For a larger system, 3 tons and up, ...") so a wrong match is visible to the customer. An answer that matches no option is **re-asked once**, offering the options in the owner's words; still no match, the default sentence goes out, and the owner sees the raw words on the card.
- **D-07:** **Mixed reply ("How much is the diagnostic, and do you work on Carrier units?").** The reply is two parts. Code sends the price sentence; the model's non-price words always go through all three Phase 2 D-01 checks on their own, so a number the model writes still holds. Both pass: **one combined text, price sentence first**, one sign-off, one count against the reply cap (Phase 2 D-52), the Phase 2 D-50 disclosure leading it when it is the first automated text. Price sentence passes and the model's part holds: the price sentence goes out with an **owner-written partial holding reply** in the same text ("I've passed your other question to {owner_name}..."), a new entry in `rules/replies.md` checked at sync like the others; the held part becomes the draft. Why: the customer must know the unanswered part is with a person, not ignored.
- **D-08:** **No clear service.** "How much for a repair?" with two candidate services: the agent asks which system (an intake-style question that sends on its own under the normal checks), then code sends that service's sentence. The model names no service, or a slug not in the folder: it holds as a price draft with the holding reply. **Each price sentence must name its own service** ("AC repair starts with..."), so a wrong pick is visible to the customer and the correction rule (D-09) re-sends the right one. The sync refuses a price sentence that does not contain its service's name (Claude's reading of "must"; Ian to confirm at plan review if he meant README guidance only). "Both" sends both sentences in one text.
- **D-09:** **Change awareness.** Code records which price sentence went out last in the conversation. A corrected intake answer (a new row, Phase 2 D-34) that maps to a **different** sentence sends it right away; one that maps to the **same** sentence sends nothing; a correction to "not sure" sends the default sentence. The customer asking again with no change re-sends the last sentence. Each re-send carries an **owner-written lead** chosen by code from the amounts: **"same"** when nothing changed, **"higher"** when every new amount is above the old, **"lower"** when every one is below, **"changed"** when the ranges overlap. Leads live in `rules/replies.md`, checked at sync; the model never writes the comparison. Why: a customer left holding a lower number in writing loses trust when the real quote comes.
- **D-10:** **Sync checks on price sentences:** every amount must match the file's prices (its `price_cents`, or the range fields the sentence is keyed to); **no** price or discount-phrase check (the furnace file's "waived" is a discount phrase in `CodeChecks::DISCOUNT_PHRASES` and must not block the owner's own terms); the **promise** and **never_say** checks stay. The promise check is what keeps a price sentence from becoming binding ("guaranteed", "for sure" are refused at sync). Estimate wording is recommended in the folder README with an example, not enforced.
- **D-11:** Price and offer sentences follow **every existing stop**: nothing in a paused conversation (Phase 2 D-24), nothing after STOP (Phase 2 D-40), each counts against the reply cap (Phase 2 D-52). Life-safety still goes first (Phase 2 D-17).

### Offer sentences (reopens Phase 2 D-08 for discount; Ian's explicit call)
- **D-12:** **Same shape as price.** The folder lists offers; each has an owner-written **conditional** offer sentence ("If you're a first-time customer, we're running a promotion that takes $50 off your first visit"), its amount or percentage fields, a **required start date** and an **optional end date**. The business confirms eligibility at the visit. Why: a conditional offer the owner already published promises nothing new, and making every offer wait for approval brings back the delay. — **Reversibility:** costly — a new folder file type and sync contract.
- **D-13:** **Code never decides whether this customer qualifies.** It only checks the offer is **live today**: start and end dates in the business's time zone, end date inclusive. When the label is `discount` and offers are live, code sends **every live offer's sentence in one text**, and Jev is skipped. A mixed reply follows D-07's split rules.
- **D-14:** **No live offer:** the owner-written **discount holding reply** (Ian's warm deferral: "We like to take care of our customers. I'll make sure {owner_name} knows you asked about a discount and he'll pick up the thread.") goes out and the owner is alerted (Phase 2 D-14 and D-20 apply). A missing discount reply falls back to `holding_reply`.
- **D-15:** **Sync checks on offer sentences:** amounts and percentages must match the offer's fields; **no** discount-phrase check; promise and never_say stay.
- **D-16:** The **Business Folder page warns** about any offer live more than **90 days with no end date**. The warning never blocks a send. Why: a forgotten standing offer costs money on every quote, and with the owner out of the loop nobody else will notice.
- **D-17:** Phase 3's walk-test example "the agent would now quote a price" is **reworded to mean a price that is not in the folder** (ROADMAP.md updated by this discussion).

### A second question while one waits (amends Phase 2 D-28)
- **D-18:** **Touches flag.** The agent's structured output says whether the new message **touches the waiting question**. Only a **clear no** lets a passing answer send while the old draft stays live, untouched, with its alert. **Yes or blank:** today's Phase 2 D-28 path, one fresh draft covering the whole thread replaces the old one. There is still at most one live draft. Why: "Actually Friday works better" answered on its own would leave a live Thursday draft that sends the wrong day. — **Reversibility:** costly — changes the draft lifecycle every later phase builds on (02.2 reply codes, Phase 3 booking).
- **D-19:** **Split.** A message that both touches the waiting question and asks something easy ("Do you do heat pumps? Also Friday might work better") is split: the easy part may send on its own, everything touching the waiting question becomes the new draft replacing the old (Phase 2 D-28). The split-off part goes in the same text as the partial holding line (D-20).
- **D-20:** **Label guard.** While a draft waits, an answer may send only if its label is `faq_answer` or `intake_question`, **never `scheduling`**, and it still passes all three Phase 2 D-01 checks (Jev's intent bar is the second look at a mixed reply). The guard applies **on a split**, and **whenever the waiting draft's own label is `scheduling`** (code reads it from the stored verdict, Phase 2 D-07), regardless of the touches flag. Otherwise every `send_on_own` label can send, scheduling included: a booking reply goes out while a price or discount question waits. Why: holding booking behind an unrelated question slows the step that finishes the conversation, and the label floor keeps the model from committing to a day while one is with the owner.
- **D-21:** **A price draft solved by a sentence.** When a waiting draft held on **price alone** (from its verdict) and a price sentence now fits (the customer named the service), code sends the sentence and **closes the draft as `answered`**: a new draft resolution kept for the labeled data (Phase 2 D-07), a timeline entry saying why, no alert, and Send (or a 02.2 reply code) refused with "Already answered". If the draft also held on anything else (complaint, promise), the sentence still sends and a fresh draft replaces the old one for what remains (Phase 2 D-28), so the owner still sees it. — **Reversibility:** costly — a new `DraftResolution` value in the calibration dataset (gate:export, D-02).
- **D-22:** **Owner alert.** An answer sent while a draft waits sends **no new alert** (Phase 2 D-22 unchanged). Safety net: a waiting draft with newer customer messages shows **"The customer wrote again since this draft"** above Send.
- **D-23:** **Prompt fix:** the agent is told never to mention a question already with the owner; the holding reply covered it.

### Holding replies and the customer who waits (amends Phase 2 D-14 and D-22; keeps D-51)
- **D-24:** **Principle for this phase and after: customer-first communication.** A waiting customer is reassured until they are contacted. The wording, timing and how much is the owner's call per business, captured at onboarding (see Owner setup questions).
- **D-25:** **Phase 2 D-51 stays exactly as it is** for `{next_open}`. New fill-ins sit beside it, each computed in code from `hours.md` so it is always true: one for **"today if he can, or after we open at 8 am tomorrow"**, one for **the next opening time alone**, and an optional **check-in time**. The owner chooses which to use; the promise is not fixed for every business.
- **D-26:** **Check-in time:** an owner setting, **off by default**: a number of hours after the next opening following the hold (8 am + 2 = "10 am tomorrow"), closures skipped; a hold at 9 am on a Tuesday still gets Wednesday's time; a result after closing uses closing time. A reply that uses the check-in fill-in while the setting is off fails the sync in plain words.
- **D-27:** **The example folder's holding reply is rewritten in the customer-first voice** and promises a place in line, not a time ("I've passed this to {owner_name} and you're on his list, and he'll get back to you as soon as he can after we open..."); "answers questions like this himself" goes. Why: several overnight texts each promised "first thing" commit the owner to more than he can keep.
- **D-28:** **Check-in reply.** A customer who checks in while a draft waits ("just checking in, haven't heard back") gets the owner-written **check-in reply**, **every time**, not only the first (like the handoff reply, which `SendFixedReply` already sends every time a customer asks again), bounded by the reply cap (Phase 2 D-52). **Each check-in alerts the owner right away** (amends Phase 2 D-14 and D-22).
- **D-29:** **Added-info reply and the code guarantee.** `rules/replies.md` also gets an **"added to your question"** reply ("Got it, I've passed that along to {owner_name} with your question."). **Code guarantee:** if a customer writes while a draft waits and the run sends them nothing, code sends one of the two: the agent's structured output picks check-in or added-info, and **unsure means added-info**, so a missed detection still reassures. **Only a check-in alerts the owner**; new info updates the draft quietly per Phase 2 D-22, because under D-28 the fresh draft already covers it and the old wording can't be sent.
- **D-30:** **Partial holding line bookkeeping.** The partial holding line (D-07, D-19) goes in the same text as the answer it rides with and **counts as the holding reply for the new draft**. Implementation note: `SendFixedReply::holdingAlreadySent()` ends the wait when any real answer is sent after a holding reply, so the partial line must be recorded where that check counts it (a holding-reply kind or equivalent); otherwise a full holding reply follows as a second text. Same for a price or offer sentence sent with the partial line.
- **D-31:** **Per-reason holding replies:** **discount** gets the warm deferral (D-14; falls back to `holding_reply`), **complaint** gets its own owner-written holding reply, **required in every folder** because a complaint can arrive anywhere, checked at sync (promise and never_say apply). Price, promise and other keep `holding_reply`. More per-reason replies wait until an owner asks.
- **D-32:** **Required only where used.** The sync requires each new reply only when the folder uses the feature that sends it: the four price leads once any service has price sentences; the discount reply is optional (falls back); the **partial holding, check-in, added-info and complaint** replies are **always required**, because the code guarantee, splits and complaints can send them in any folder. The sync names what is missing in plain words. — **Reversibility:** costly — new required fields in `rules/replies.md` for every client folder.

### Example folder
- **D-33:** `examples/example-hvac` changes with the phase: a replacement or new-system service file (intake: current unit with owner-defined size options, condition, ductwork; answer-keyed price sentences and a default sentence); price sentences on the repair files (the $89 diagnostic); `furnace-tune-up` keeps `price_policy: none`; one example offer; the rewritten holding reply (D-27); every new reply (D-07, D-09, D-14, D-28, D-29, D-31); the README guidance recommending estimate wording (D-10). All fictional (CLAUDE.md rule).

## Specific Ideas

- Ian's frame: answers come from the business's knowledge base, set up with the owner at onboarding; an agent that always defers to the owner hurts speed to lead. Edge cases get settled in the setup conversation with each business.
- The pool-company story: the customer sent measurements and wanted a ballpark; the company insisted on a visit; the customer went elsewhere. Transparent pricing wins customers (Endless Customers; a pricing calculator on a website is the same idea).
- The upstairs unit: "an upstairs unit normally runs between $4,000 and $7,000", after current unit, condition and ductwork.
- The default sentence example: "No problem if you're not sure what you have. Smaller units typically run $2,000 to $5,000 installed, larger ones $5,000 to $10,000. We'll lock in an accurate quote once we see your setup."
- The offer sentence example: "If you're a first-time customer, we're running a promotion that takes $50 off your first visit."
- The discount warm deferral: "We like to take care of our customers. I'll make sure Mike knows you asked about a discount and he'll pick up the thread."
- What matters most in the holding reply: the customer is sure they are in a queue and will not be dropped, since many businesses never respond.

<objective>
Tie a failed front-desk run's report to exactly the burst that run claimed. ProcessInbound makes a claim token when it is built, the claim writes that token onto every row it takes, and failed(), which runs on a fresh copy of the job after a timeout or a dead worker, finds the burst by the token instead of guessing by id (WR-22). This plan covers the token and the failed() path; plan 06-07 makes the report once per token on both paths.

Purpose: ALRT-02 and success criterion 5, D-10, D-12, D-13, D-20 (failed() path), D-21.
Output: one migration, the token in ProcessInbound and ClaimInboundBurst, failed() by token, ReportFrontDeskFailure::subjectOf(), a factory state, a new test file, the four named FrontDeskFailureTest changes, one walk-through line, the BLUEPRINT Built bullet (written in Task 1, extended in Task 2) and a queue-drain deploy note in the SUMMARY.

Existing tests this plan changes, named: the four FrontDeskFailureTest cases in must_haves, which build their claimed rows with handled_at only; their titles and assertions stay. All four come after both wraps (success criterion 1, D-15). Three would fail outright once failed() selects by token; the fourth ('does not tell the owner twice ... (WR-03)') would still pass while testing nothing, which is why it is re-pointed too (see the sweep under Flagged assumptions). Every other front desk, alerts and inbound test passes unchanged. ReportFrontDeskFailure::handle()'s signature does not change (four callers, research Pitfall 5).

Chokepoint rule: no agent action is added; the report is code (D-09 applies to the alert it raises).

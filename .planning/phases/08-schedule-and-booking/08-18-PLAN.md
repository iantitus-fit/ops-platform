**(b) What happens to rows and card files written before the fix.** The links themselves are revoked; the stored text is not rewritten. A one-time migration sets revoked_at on every booking link that has not booked and is not already revoked: open, superseded and expired ones alike (revoking a superseded or expired link changes nothing a customer can do, and it also keeps WithdrawUnsentLink from ever putting one back). That is the only change that reaches copies that already exist: a backup or copy of the database or the folder taken before the fix, the text provider's own log of those texts, the session rows, and the fake carrier's local log all hold the old token, and from the moment the migration runs none of those tokens can book. Rewriting the stored bodies to /book/[link] would only clean copies made afterwards, would destroy what was sent, and cannot be undone, so it is not done. A link that has booked is left alone, because its page shows the customer their visit (U-14) and can never book again (D-13). Then the migration queues a card redraw (CustomerRecordChanged, the 04-05 precedent) for every contact who holds a revoked link or a message holding a booking address, and RecordsWriter, which 08-17 made hide every booking address, rewrites the card, customers/INDEX.md and open-leads.md, so the folder copy holds no token text either. No real customer exists before the first deploy, so in practice this touches only development databases; the migration is still written for a live one.

Reversibility: rated `reversible` (see Task 1): no row is deleted and no text rewritten; putting a link back is one update of revoked_at for the ids the migration logs; cards redraw from the database at any time. No checkpoint is needed under planner-reversibility.md. The alternative it rejects, rewriting stored bodies, would be one-way.

Close gap D-12 going forward (08-VERIFICATION.md, status failed; T-08-01 and T-08-27 in 08-SECURITY.md): from this plan on, no stored or printed copy of a sent text holds a working booking link, while the customer still receives one. Purpose: D-12 says a copy of the database holds no working link. Today OutboundSender stores the full text, token included, as messages.body, and CustomerCard prints it into records/. A copy of the database or the business folder therefore holds working links.

**(a) How the customer still gets the real link while every stored or printed copy carries a form that does not work.** One pure function, `App\Support\BookingLinkTokens::hide()`, writes every booking address it finds (`/book/` followed by the 64-hex token) as `/book/[link]`. OutboundSender is the one path every text to a customer takes (06 D-09; CLAUDE.md chokepoint rule), so it is the place to split the two copies: it keeps the text it was handed in memory, hands that text to the text channel, and stores only the hidden copy, in send() and in sendExisting() alike. The agent's scheduling reply, the owner's approved draft (D-45) and every other sender are covered there at once. Everything that copies a sent text reads the stored row, so it carries the hidden form with no change of its own: the customer card and open-leads.md in records/, the timeline, owner alert quotes, and the conversation history the front desk later reads. Where a copy can come from something other than the stored row, the same function is applied where that copy is written: the failed-send record (meta.error, the "Reply not sent:" note, and the DomainException text, whose raw previous exception is dropped when it held a token); the fake carrier's local log line; a customer's own text that pastes the link back (RecordInbound); every file RecordsWriter writes; and the address a page visit leaves in the session as its previous URL (database sessions in production). Queued jobs carry only ids (RenderCustomerCard's contact id, ProcessInbound's message and conversation ids), so a payload in jobs or failed_jobs cannot hold the link, and failed_jobs' exception text can only receive it through an exception message, which the failed-send scrub covers; the leak test proves both. The text provider's own message log (Twilio keeps every sent body) and the host's request log of page addresses are outside the platform; 08-18 puts them on the attorney list and the open items.

The hiding is by pattern, not by remembering the token, so it also covers a token that reaches a string by any route (a customer's paste, an exception message) without the token being carried around. A bare 64-hex string with no `/book/` before it, such as booking_links.token_hash, is left alone, because only an address works.

**(c) How the leak test enumerates tables on both drivers.** `Schema::getTables()` lists every table on the connection: on SQLite from pragma_table_list (SQLite's own sqlite_ tables left out), on Postgres from pg_class over every schema except information_schema and the pg_ ones. Each table is read through its `schema_qualified_name` (main.x on SQLite, public.x on Postgres) with DB::table(); every column value is turned into text (a stream from a Postgres bytea column is read out) and searched for the token, raw and, when it is valid base64, decoded, because the database session driver stores its payload base64-encoded. The listing must hold messages, activities, booking_links, owner_alerts, jobs, failed_jobs, sessions and cache, and a planted token must be found, so a broken listing or search cannot pass. The test also searches every file under the business folder, every log record and every job payload. CI's pgsql leg runs it on Postgres (recorded in WINDOWS.md, never a pause).

**(d) The front desk's own words never carry a booking address (Ian, 2026-11-07, adds to D-12; Task 3).** Once stored texts and the card read '.../book/[link]', the model sees that line in the conversation history and may copy it into a new reply, and the customer would get a broken link. This is enforced in code, not in the prompt, in two places. First, the send rule that judges the front desk's words before any send: `DecideSendOrDraft::decide()`, whose code checks already hold a reply as a draft with a reason, holds a reply whose model words contain '/book/' in any letter case. The match rule is a case-insensitive substring test for '/book/' on `$run->reply->reply`, the model's words alone, so it catches the placeholder '/book/[link]', a '/book/<token>' path and a full URL alike. The reply is held as `code:booking_link` and the owner reads "Held: writes its own booking link, which would not open". The check runs before `RunFrontDesk::sendPassingReply()` appends the owner's link line, and it never reads that line, the disclosure or the sign-off, so a passing scheduling reply still carries its working link. Second, the chokepoint: the held draft's own text holds '/book/[link]', and an owner who approved it unedited (SendOwnerReply, D-45) would send the placeholder. `OutboundSender::whyBodyIsRefused()`, which every sender passes before a row is written or a draft claimed, refuses any text holding '/book/[link]' with a plain sentence the owner sees (`OutboundSender::HIDDEN_BOOKING_LINK`). On the approval path the refusal comes after the link is minted, and SendOwnerReply's existing catch withdraws it and puts back the link it superseded, as D-45 asks of any refused send; the send stays on the owner path through `sendExisting()` and the link is still added at approval, never into the draft, so D-45 stands. Only the hidden form is refused, so the link line with a real token, and an owner's own web address that happens to hold '/book/', still go out.

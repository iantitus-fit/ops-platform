# Sprint 1: Text Front Desk

Status: in progress. `.planning/` is the plan of record: this file is the
sprint's acceptance list and the walk-through log, and phase 2 in
`.planning/ROADMAP.md` holds the plans.

## Goal

A customer who texts gets a reply that moves the conversation forward without
the owner, from an agent defined in a file, and nothing risky is ever sent
without the owner. The agent's provider, model and fallbacks are edits to its
`agents/*.md` file that go live through the normal sync, and the real Twilio
driver sits behind the same `TextChannel` interface as the fake one.

## Done when (acceptance criteria)

1. A customer who texts through the fake channel (for example from `/dev/chat`)
   gets a reply from the agent in the same conversation. The first reply says it
   is an AI, uses the voice file's sign-off, and never uses a `never_say` phrase.
   The agent then asks the matching service's intake questions, and the answers
   show on the timeline and the customer card.
2. A message involving a price, a promise, a discount or a complaint is never
   sent: it appears as a draft in the dashboard and the owner is alerted, while
   intake questions, scheduling and FAQ answers send on their own, even when a
   scripted model tries to send the draft.
3. The owner can take over a conversation so the agent stops replying until it
   is handed back, and can approve, edit and send, or discard a draft from the
   dashboard. A customer who asks for a person is handed to the `escalate_to`
   contact.
4. Changing an agent's provider, model or fallback list is an edit to its
   `agents/*.md` file that goes live through the normal sync. A broken agent
   file is rejected with a plain-words message, and when the primary provider
   fails the agent falls through to its fallback.
5. The Twilio text driver sits behind the same `TextChannel` interface and is
   selected by config alone, verified against Twilio-shaped payloads. Going live
   on Ian's test number follows A2P approval and does not gate this phase. The
   full Pest suite passes on PostgreSQL in CI as well as on SQLite locally.

## Notes for testing

- In Phase 2 your own phone is treated like a customer's. If you reply to an alert text, the front desk answers you as a customer and may hold a draft and alert you again.
- Approving a held draft by replying to its alert text arrives in Phase 2.1. Until then, open the link in the alert and approve it on the conversation page.
- Replying STOP to an alert stops every alert until you text START.
- Alerts go to the phone on your profile page (open it from the user menu in the top corner). With no phone saved, the Business Folder page says so and alerts have nowhere to go.
- The login page has Remember me ticked. Open an alert link while signed out, sign in, and you land on that conversation.

### Before a real client

Customer texts, the thread and the customer card are sent to the model providers named in the agent file. Do these checks before the first real client's text goes through, for every provider an agent file names (the primary and each fallback), and again whenever a provider is added to `agents/*.md`:

- Read each provider's data processing terms for how long they keep what is sent to them, and whether they train on it.
- Test with OpenRouter's zero-data-retention enforcement on, so a provider that would keep the text is refused instead of used.
- Pin the provider for each model, so a request cannot be quietly routed to a different one. This is the same check Jev needs.

## Walk-through log

One line per concept, added the first time it shows up in this sprint.

- GitHub Actions workflows and service containers (plan 02-01): `.github/workflows/tests.yml` is a recipe GitHub follows on every push. Its `pest` job runs the whole suite twice, once per entry in `matrix.database` (`sqlite` and `pgsql`), and the `services:` block starts a throwaway `postgres:17` container next to the job, with a health check so the tests wait until the database answers. The two actions it uses are pinned to full commit ids, so a changed tag upstream cannot change what runs.
- Environment variables beat `phpunit.xml` (plan 02-01): the `<env>` lines in `phpunit.xml` are defaults, and PHPUnit does not overwrite a variable that already exists. The workflow sets `DB_CONNECTION: pgsql` on the job, so the same test files run on Postgres in CI with no config change, and on your Mac you do the same by putting the five `DB_*` variables in front of `php artisan test`.
- `Http::preventStrayRequests()` (plan 02-01): in `tests/Pest.php`, inside the `beforeEach` that runs before every Feature test, this tells Laravel's HTTP client to throw on any request that no `Http::fake([...])` matches. A test that forgets to fake the model provider, Jev or Twilio now fails loudly instead of sending a real request with a real key, and `tests/Feature/Quality/TestSafetyNetTest.php` proves it, along with a check that the database driver in use is the one the run asked for.
- laravel/ai providers (plan 02-02): `config/ai.php` names each provider the app can talk to (`anthropic`, `openai`, and so on). `Ai::textProvider('anthropic')` builds one without calling it, which needs no key and no network; it throws when the name is unknown or when that provider cannot write text (`typesafe` only classifies). The sync uses that to check that an agent file names a provider that can write replies, and the Business Folder page shows the chain: the primary model first, then each fallback in file order.
- Claiming a row with a conditional update (plan 02-08): `Message::query()->whereKey($id)->whereNull('dispatched_at')->update([...])` is one SQL statement that changes the row only if the column is still empty, and `update()` returns how many rows it changed. Two requests racing for the same message cannot both get 1 back, so only one of them goes on to queue the job. `DispatchInbound` uses it so a text is queued exactly once, and `ClaimInboundBurst` uses it per row (with `handled_at`) so two runs never answer the same texts. No cache or lock is needed because the database settles the race.
- Debounced jobs (plan 02-08): `#[DebounceFor(20, maxWait: 90)]` on `ProcessInbound` tells Laravel to delay the job 20 seconds, and to replace it with a fresh delay when another job with the same `debounceId()` is queued (here the conversation id), so three quick texts become one run roughly 20 seconds after the last, and never later than 90 seconds after the first. The waiting token lives in the cache and can disappear, so the database claim above is what keeps a stray second run harmless. The sync queue in tests ignores delays, so the tests use `Queue::fake()` and call `handle()` directly.
- Data migrations (plan 02-08): a migration can change rows as well as tables. `2026_10_12_000002_backfill_dispatch_columns_on_messages.php` copies `created_at` into the two new columns for every existing message, with `DB::raw('created_at')` so the database does the copy in one statement. It is separate from the migration that adds the columns so a test can run it against rows it set up itself.
- Static methods and word-boundary patterns (plan 02-03): `CodeChecks::findings($text, $neverSay)` is called on the class itself, with no `new`, because it keeps no state between calls: the same text and lists always give the same answer. Each phrase becomes a regular expression with `\s+` between words, a character class so a curly and a straight apostrophe match alike, and `(?<![\p{L}\p{N}_])` and `(?![\p{L}\p{N}_])` at the edges, which mean "not directly next to another letter or digit". That is why `compromise` is not `promise`. The `iu` flags at the end make it ignore case and read the text as UTF-8, so accented letters work too.
- Cross-file validation (plan 02-03): a rule string like `required|string` can only look at one file's own fields. The reply texts must be checked against the `never_say` list in a different file, so `Validator::repliesErrors()` is a method that receives every loaded file and picks the voice file out of the same folder. It reads the candidate folder, never `ActiveConfig`, because the folder is not live until the sync accepts it.
- The scheduler (plan 02-09): `Schedule::job(new SweepUndispatched)->everyFiveMinutes()->withoutOverlapping();` in `routes/console.php` tells Laravel to put that job on the queue every five minutes, and `withoutOverlapping()` skips a run while the previous one still holds its lock. Something has to wake the scheduler each minute: locally `php artisan schedule:work` does it, and `AppServiceProvider` adds it to `composer run dev` (through `DevCommands::artisan`, only when the app is local). Production needs one cron line running `php artisan schedule:run` every minute, which arrives with the first deploy. The sweep leaves texts younger than two minutes to the webhook and older than 24 hours alone, and the backfill migration from plan 02-08 gave every earlier message a `dispatched_at`, so no old customer is ever texted because of it.
- Backed enums as a fixed vocabulary (plan 02-04): `enum ReplyLabel: string` in `app/Enums/ReplyLabel.php` is a closed list of the eight words an owner may write in `rules/sending.md`. Each `case` has a text value (`Price = 'price'`), and static methods on the enum hold the rules about them: `sendOnOwnAllowed()` is the three that may send on their own, and `neverOnItsOwn()` is the price, promise, discount and complaint floor. Because the floor is a method in code, `Validator::sendingRulesErrors()` and, later, the send path can ask the same question and cannot disagree. `AlertReason` does the same for owner alert events and adds `plainWords()`, a `match` over `$this` that turns each case into the words an owner reads.
- A second validator for a nested map (plan 02-04): the main rules in `rulesFor()` only say `owner_alert` is required. When it turns out to be a map, `Validator::ownerAlertErrors()` builds a second `LaravelValidator::make($alert, [...])` for its own fields (`channels`, `right_away`, `after_hours`) and prefixes each failed field with `owner_alert.` so `PlainWords` can say "owner_alert right_away item 1 must be one of ...". Rules that depend on a list's contents, such as "right_away must include life_safety", are plain PHP after that, because a rule string cannot express them.
- Dates in a time zone with Carbon (plan 02-05): `CarbonImmutable::parse('2026-10-13 16:30', 'America/Chicago')` reads that wall-clock time as Chicago time, and `->setTimezone('America/Chicago')` shows any other moment on the Chicago clock. `BusinessClock` converts every moment to the business zone first and then does all its sums there (`setTimeFromTimeString('08:00')` for the opening, `addDays()` to step to tomorrow), never in UTC. That is why a weekend where the clocks go back still says "8 am": 8 am Monday is 13:00 UTC before the change and 14:00 UTC after it, and working in the business zone lets Carbon sort that out. `CarbonImmutable` returns a new date from every call instead of changing the one you hold, so `$local->addDay()` cannot silently move `$local`. In tests, `$this->travelTo(...)` freezes what `now()` returns, so a test that depends on "right now" gets the same answer on every run; `BusinessClockTest` instead passes each moment in directly, which needs no frozen clock at all.
- The HTTP client and faking it (plan 02-06): `Http::withToken($key)->acceptJson()->connectTimeout(3)->timeout(8)->post($url, $body)->throw()` in `JevClassifier` is Laravel's built-in client. `withToken` adds the `Authorization: Bearer ...` header, the two timeouts mean a slow Jev gives up quickly (a later plan turns that into "hold the draft"), and `throw()` turns any 4xx or 5xx answer into an exception instead of a quietly bad response. Laravel sends the PHP array as JSON for you. In tests `Http::fake([...])` answers in place of the real server, `Http::preventStrayRequests()` (switched on for every Feature test in `tests/Pest.php`) makes any call nobody faked throw, and `Http::assertSent(fn (Request $request) => ...)` lets a test inspect exactly what would have gone out, which is how `JevClassifierTest` proves the body holds only the model, the two texts and the questions.
- Readonly classes and building from config (plan 02-06): `readonly class TriageQuestions` means every property is set once in the constructor and can never change, so a question list cannot be altered after it is built. `TriageQuestions::fromConfig(app(ActiveConfig::class)->triage())` is a named constructor: a static method that turns the owner's `rules/triage.md` (read back through `ActiveConfig`, never from the folder) into that object, putting `other` first because Jev leans toward the first option it is shown.
- Factory states and nullable foreign keys (plan 02-10): `UserFactory::withPhone('+12025550199')` is a state, a small method that returns the factory with a few columns changed, so a test reads `User::factory()->withPhone()->create()` instead of spelling out the column. In the `owner_alerts` migration, `foreignId('user_id')->nullable()->constrained()->nullOnDelete()` makes a column that points at a user row but may be empty, and tells the database to set it to empty if that user is ever deleted, so the alert's record outlives the person. `conversation_id` uses `cascadeOnDelete()` instead because an alert means nothing without its conversation.
- An action that never throws (plan 02-10): `SendOwnerAlert::handle()` wraps the text channel call in `try { ... } catch (Throwable $exception) { ... }` and writes the failure onto the alert row (`failed_at` and `failure`) instead of letting it escape. The code that raises an alert is in the middle of handling a customer, so a phone that refuses texts must not break that; the cost is that a failure is only visible if something reads the row, which is why plan 02-11 adds a timeline note and plan 02-12 a warning. `report($exception)` still writes it to the log. A check at the top (`sent_at`, `skipped_at` or `failed_at` already set) makes calling it twice harmless.
- Regular expressions with a callback (plan 02-10): `OwnerAlertText::clean()` uses `preg_replace` to swap patterns for placeholders, and `preg_replace_callback` for phone numbers, because the pattern `\+?[\d(][\d\s().\-]*\d` matches any run of digits and punctuation, and only the callback can count the digits in what matched and leave a short run like "3" alone. The order of the calls is part of the design: web addresses go first, emails second, so `dana@example.com` becomes `[email]` and not `dana@[link]`. `mb_scrub()` runs first so broken UTF-8 from a customer cannot make a pattern fail and return nothing.
- Catching what the HTTP client throws (plan 02-07): `->throw()` turns a 4xx or 5xx answer into a `RequestException` and a refused or timed-out connection into a `ConnectionException`, and `JevClassifier` catches each in its own `catch` block and throws `ClassifierFailed` instead, so the rest of the app only has to know one failure. The message carries the status number and never the key or the texts, and the original exception rides along as the third argument (`new ClassifierFailed($reason, 0, $previous)`) so a log can still show the cause. `Http::failedConnection()` in a test makes the fake behave like a timeout, and `Http::assertNothingSent()` proves a refusal (a blank key, a `latest` model) happened before any request left.
- Swapping an interface for a fake in tests (plan 02-07): `AppServiceProvider` binds `Classifier` to `JevClassifier`, so asking the container for the interface gives the real thing. `tests/Pest.php` then runs `$this->app->instance(Classifier::class, new FakeClassifier)` before every Feature test, which tells the container to hand out that one scripted object instead, so no test can reach Jev. `fakeClassifier()` returns it for a test that wants to script an answer (`->answer('faq', 0.9)`), make it fail (`->failWith('down')`) or read back what it was asked (`->calls()`). A test that wants the real class calls `$this->app->forgetInstance(Classifier::class)` first.
- Comparing floats and testing the edges (plan 02-07): `TriageReading::read()` compares Jev's numbers with `>` and `>=` exactly as they arrived in the JSON, with no rounding, because the thresholds are the rule and a rounded 0.0751 would quietly become 0.075. `TriageReadingTest` uses a Pest dataset (`->with('jev readings')`), a named list of rows run through the same test body, to pin each edge: 0.85 sends and 0.8499 holds, 0.075 is a clear no and 0.0751 is not. A short arrow function (`$yes = fn (string $key): float => $result->yesNo[$key] ?? 1.0;`) reads one answer and treats a missing one as a certain yes, so an answer that never arrived can only hold a reply, never let it through.
- Dates are stored as wall-clock text (plan 02-11): Eloquent writes a Carbon date into a `datetime` column as the text its own clock shows (`2026-10-14 08:00:00`) and does not convert it, and reads that text back in the app's time zone (here UTC). `BusinessClock::nextOpening()` hands back 8 am on the Chicago clock, so `RaiseOwnerAlert::dueAt()` calls `->setTimezone(config('app.timezone'))` first; without it the alert would be stored as 8 am UTC, which is 3 am in Chicago, and the first version of `OwnerAlertTimingTest` caught exactly that. The rule is: convert to the app's zone on the way in, and convert to the business zone only for display.
- A sweep that walks a table (plan 02-11): `SendDueAlerts` asks for the alerts with no `sent_at`, `skipped_at` or `failed_at` whose `due_at` has passed, and `->lazyById()->each(...)` reads them in small batches ordered by id instead of loading them all at once, which stays safe even while the loop changes the rows it is walking. Each alert ends in exactly one state, so a second run finds nothing left to do. A timeline entry is an `Activity` row whose `subject_type`/`subject_id` point at the alert (a polymorphic relation), and `CustomerCard::section()` is a `match` over `ActivityType` with no default arm, so adding the new `OwnerAlerted` case without a card line would throw: the compiler-style safety net is the point.
- Custom Filament auth pages (plan 02-12): `->profile(EditProfileWithPhone::class)` and `->login(RememberedLogin::class)` in `AdminPanelProvider` hand Filament your own class in place of its default page. Each class `extends` Filament's page, so it keeps everything the parent does and overrides one part: `EditProfileWithPhone::form()` lists the parent's field builders plus a phone box, and `RememberedLogin::getRememberFormComponent()` calls `parent::getRememberFormComponent()` and adds `->default(true)`. The phone box stores `PhoneNumber::toE164()` of what was typed through `dehydrateStateUsing`, and a closure passed to `->rule()` calls `$fail(...)` with a plain sentence when that returns null (Laravel skips a rule on an empty box, so clearing the phone saves null).
- Returning to the page you asked for (plan 02-12): when a signed-out visitor opens `/admin/conversations/12`, Laravel's `redirect()->guest(...)` stores that address in the session as the "intended" URL before sending them to the login page. Filament's `LoginResponse` ends with `redirect()->intended(Filament::getUrl())`, which sends them to the stored address, or to the panel home when there is none. That is why an alert link survives a sign-in, and `ProfileTest` proves it by requesting the conversation URL as a guest and then signing in through `RememberedLogin`.
- laravel/ai agents (plan 02-13): `app/Ai/Agents/FrontDeskAgent.php` is a class the SDK prompts. It `implements Agent, Conversational, HasStructuredOutput` and `use Promptable`, which gives it a `prompt()` method. `instructions()` is what the model is told, `messages()` is the thread so far, and `schema()` makes the model answer in named fields (`reply`, `label`, and so on) instead of free text; the app then checks those fields in `AgentReply::fromStructured()`, because an answer from a model is untrusted input. It has no tools, so the model has no way to send a text, only to propose one. In tests `FrontDeskAgent::fake([...])` returns scripted answers instead of calling a provider, and `preventStrayPrompts()` makes any prompt nobody scripted throw, so `tests/Pest.php` turns it on before every Feature test and `scriptFrontDeskReplies()` scripts the answers. `RunFrontDeskAgent` prompts one provider at a time with `provider: ['anthropic' => 'claude-sonnet-5-5']`, because the SDK's own failover only covers connection errors, 429, 402 and overloaded answers, not a 500, a bad key or broken JSON.
- Cache locks that wait or give up (plan 02-14): `Cache::lock("reply:{$conversation->id}", 30)` asks the cache for a lock with that name that frees itself after 30 seconds. `->get()` tries once and answers true or false, which is what the owner's send uses so the owner is told at once when a reply is in flight. `->block(5)` keeps trying for up to five seconds and throws `LockTimeoutException` if it never gets the lock, which is what the front desk uses, because the owner's send is short and the agent can wait its turn. `OutboundSender` takes the same lock name as `SendOwnerReply`, so an agent text and an owner text to one customer can never go out together, and a `try { ... } finally { $lock->release(); }` frees the lock even when the send throws.
- Holding back one job in tests (plan 02-14): `Queue::fake([ProcessInbound::class])` in `tests/Pest.php` fakes only the named job, so it is recorded and never run, while every other job still runs on the sync queue as before. `runQueuedFrontDeskJobs()` then reads the recorded jobs with `Queue::pushed(ProcessInbound::class)` and runs each one once through `app()->call([$job, 'handle'])`, which fills in the `handle()` arguments from the container the way the real worker does. A test decides when "20 seconds later" happens by calling it.
- Casting columns to enums and JSON (plan 02-14): in `Message::casts()`, `'kind' => MessageKind::class` makes Eloquent hand back an enum case when you read the column and accept one when you write it, and `'gate' => 'array'` turns the JSON column into a PHP array both ways. The send rule's verdict (`Verdict::toAttributes()`) is just an array of those four column names, so `$conversation->messages()->create([...$attributes, ...$verdict->toAttributes($label)])` stores a whole verdict in one call, and the `...` spread puts the later array's keys over the earlier one's.
- Locks that wait versus locks that tell you at once (plan 02-15): the front desk and the owner's reply box both take `Cache::lock("reply:{$conversation->id}", 30)`, but they take it differently on purpose. `OutboundSender` uses `Cache::lock(...)->block(5)` for the front desk, which keeps trying for up to five seconds so the agent waits its turn behind the owner's short send, and throws `LockTimeoutException` if the lock never frees; `RunFrontDesk` turns that into a draft held as `send_refused` instead of an error. The owner's own send uses `get()`, which tries once and answers true or false, so the owner is told at once that another reply is in flight and can look at the thread instead of watching a spinner.
- A `match` that reads a code in two steps (plan 02-15): `Verdict::plainReasonFor('code:price')` first splits the reason code at the colon into a kind (`code`) and a detail (`price`), then one `match` on the kind picks a second `match` on the detail. `label:price`, `code:price` and `classifier:price` all land on the same words, `Held: asks about price`, because the owner needs to know why, not which check noticed. The last `default` arm of each `match` means a code added later still shows a sentence instead of throwing `UnhandledMatchError`.
- Architecture tests that guard a doorway (plan 02-15): `arch('...')->expect('App\Channels\TextChannel')->toOnlyBeUsedIn([...])` in `tests/Unit/ArchitectureTest.php` reads every class in the app and fails if the `TextChannel` interface is mentioned (imported, type-hinted or implemented) anywhere outside the listed namespaces. It is how "every text to a customer goes through `OutboundSender`" stays true after this plan: a later class that asks for `TextChannel` to send directly turns the test red, and the fix is to call `OutboundSender::send()` instead. `SendOwnerReply` used to hold its own copy of the sending code; it now just checks the owner's words and hands them to `OutboundSender`, so the owner and the front desk share one lock, one set of refusals and one way of recording a failure. `RunFrontDesk` tells a channel failure from a refusal by the sentence prefix in `OutboundSender::NOT_SENT`, a `public const string`, so both sides read the same constant rather than two copies of the wording.
- Writing the record first, telling the owner second (plan 02-16): `RunFrontDesk::storeDraft()` puts the draft and its `draft_held` timeline entry inside one `DB::transaction(...)`, which hands back the saved draft, and only after that closes does it call `RaiseOwnerAlert`. A text to the owner's phone cannot be taken back, so it must not go out for a draft the database later rolled away; and if the alert send fails, the draft and its reason are already safe on the timeline. In the conversation view, `<x-filament::badge :color="match ($message->status) {...}">` is the same `match` you have seen in PHP, written inside a Blade attribute: `Draft` and `Queued` map to `'warning'`, `Sent` and `Delivered` to `'success'`, and the `default` arm is gray, so a status that never went out can never borrow the green of a sent text.
- Latest row per group, and an update that only fires when it is safe (plan 02-18): a correction is a new `intake_answers` row, never an edit, so "the current answer" is the row with the highest id for a conversation, service and question. `CustomerCard::intakeAnswerLines()` loads the contact's answers oldest first with `IntakeAnswer::query()->whereIn('conversation_id', $contact->conversations()->select('id'))` (the inner query becomes a subquery, so the database does the filtering), then `->groupBy('conversation_id')` and `->keyBy('question_key')` build the lookup: when two rows share a key, `keyBy` keeps the later one, which is the higher id. The id, not the timestamp, decides because two answers recorded in the same second share a `created_at`. For the name, `RunFrontDesk::fillEmptyName()` runs `Contact::query()->whereKey($id)->where(fn ($query) => $query->whereNull('name')->orWhere('name', ''))->update(['name' => $name])`, and `update()` returns how many rows changed: 0 means the contact already had a name (so nothing is written and no note is added), 1 means this run filled it. Putting the "only if empty" test inside the query itself, not in a PHP `if` before it, means two runs racing each other cannot both overwrite a name.
- Letting the database say no, and keeping what you replace (plan 02-17): a conversation may hold only one live draft, and `2026_10_12_000006_add_draft_resolution_to_messages_table.php` makes the database enforce it with `create unique index messages_one_live_draft_per_conversation on messages (conversation_id) where status = 'draft'`. A unique index normally refuses two rows with the same value; the `where` makes it a partial index that only looks at rows matching the condition, so any number of sent, queued or withdrawn messages can share a conversation but a second `draft` throws `UniqueConstraintViolationException` (the test creates two with `Message::factory()->draft()`). Because Laravel's schema builder has no partial-index method, the migration uses `DB::statement(...)`, and the same line works on SQLite and Postgres. `RunFrontDesk::storeDraft()` still has to avoid ever hitting that error, so inside one `DB::transaction(...)` it finds the live draft with `->lockForUpdate()` (on Postgres this makes a second job wait its turn on that row; SQLite ignores it), marks it `Withdrawn` with `resolution` `Replaced`, and only then creates the new one. Nothing is deleted: the old draft stays as labeled history. The new draft's `meta` records `replaces => [ids]`, so a third text in a row can still see that the owner was already alerted about this question, and `ownerNeedsAlertFor()` sends another alert only when the new reason is urgent and no sent alert in the chain was.
- A timestamp as an on/off switch, and checking it again where it counts (plan 02-19): `conversations.paused_at` is a nullable timestamp, so "null" means the assistant is active and any time means it stepped back, and the same column also records when. `Conversation::isPaused()` is just `$this->paused_at !== null`, and `casts()` turns `paused_reason` into the `PausedReason` enum. `PauseConversation` and `HandBackConversation` follow `CloseConversation`: inside `DB::transaction(...)` they read the row again with `lockForUpdate()` and `refresh()`, and do nothing if it is already in the state asked for, so a second tab cannot add a second timeline note. The important check is in `OutboundSender::whyBlocked()`: `deliver()` calls it after the send lock is taken and the conversation is `refresh()`ed, so a reply the agent finished writing a moment before the owner pressed Take over is refused, and `RunFrontDesk` turns that refusal into a `send_refused` draft. The test proves it by giving `FrontDeskAgent::fake(function () { ... })` a closure that pauses the conversation while the agent is "thinking" and then returns the scripted reply, which is the easiest way to make something happen in the middle of a run.
- Header actions that show and hide, and a migration that must put an index back (plan 02-19): `Action::make('takeOver')->visible(fn (): bool => ...)` in `ViewConversation::getHeaderActions()` asks the record on every render, so after `callAction('takeOver')` the page shows Hand back instead, and the test checks both with `assertActionHidden()` and `assertActionVisible()`. Adding a foreign key column (`paused_by`) to a SQLite table makes Laravel rebuild the whole table, and the rebuild brings back `conversations_one_open_per_contact` as a plain unique index, forgetting its `where status = 'open'`; the first run of the new tests caught it, because a closed and an open conversation for one customer suddenly collided. The migration therefore drops that index and creates it again with `DB::statement(...)` after the columns are added, the same way the draft index was added after its columns in plan 02-17.
- Counting rows in a time window, and a query you can reuse (plan 02-20): `RunFrontDesk::replyCapReached()` builds the question "which texts has the assistant sent in this conversation that count?" once as a small closure, `$counted = fn () => $conversation->messages()->where(...)`, and calls it twice, so the last hour and the last 24 hours are counted by exactly the same rules and only the `created_at >= now()->subHour()` line differs. A query builder is used up as you add to it, which is why it is a function that makes a fresh one each time instead of a variable. The numbers 6 and 20 are read with `config('gate.reply_cap.per_hour')`, which reads `config/gate.php`, so changing a limit never touches the action. The safety line is left out with `where(fn ($query) => $query->whereNull('kind')->orWhere('kind', '!=', MessageKind::LifeSafety))`: the extra parentheses make Laravel group the `or` so it cannot swallow the other `where` conditions, and `whereNull` is needed because in SQL `kind != 'life_safety'` is not true for a row whose kind is empty.
- Doing things in the order the doorway allows (plan 02-20): a handoff alerts the owner, sends the customer the fixed reply, and only then pauses the conversation, because `OutboundSender::whyBlocked()` refuses every automated text once the conversation is paused. Reversing the last two would make the handoff text refuse itself. `SendOwnerReply::handle(..., ?User $by = null)` pauses with `owner_replied` only after `OutboundSender::send()` returned, so a send that threw never reaches the pause line, and `PauseConversation` already leaves a conversation that is paused alone, so a take over keeps its `taken_over` reason. The Livewire thread shows the banner with `#[Computed] pausedBanner()`: a computed property is a method you read like a property in the view (`$this->pausedBanner`), recalculated on each request, so the 5-second poll picks up a pause that happened elsewhere.
- A job that skips the line, and a lock keyed on the message (plan 02-21): `RespondToLifeSafety` is a queued job like `ProcessInbound`, but it has no `#[DebounceFor]`, so it runs as soon as a worker picks it up instead of waiting about 20 seconds for more texts. `RecordInbound` queues it with `RespondToLifeSafety::dispatch($message->id, $hazard)->afterCommit()`: `afterCommit()` holds the job back until the database transaction that saved the text has finished, so the worker can never look for a message that was rolled back. In tests the queue is `sync`, which runs the job on the spot inside the webhook request, which is why a test sees the safety line before it runs any burst job. `SendLifeSafetyLine` wraps its work in `Cache::lock("life-safety:{$inbound->id}", 30)` and `->block(10)`, so the immediate job and `RunFrontDesk`'s second look at the same text cannot both pass the "has this text been answered yet?" check at once; the check reads the conversation's `life_safety` messages and looks for the inbound id inside their `meta.in_reply_to` list.
- Fixed words as constants, matched with the veto's own rules (plan 02-21): `App\SendRule\LifeSafety` keeps the hazard phrases in `public const` arrays and the three sentences in `private const` strings, so the only way to change what a customer is told is to change code. `hazardIn()` reuses `CodeChecks::phrasePattern()`, which builds a regular expression that ignores case, treats curly and straight apostrophes alike and insists on whole words, so `rotten eggs` must be listed on its own next to `rotten egg` and `fires up` can never match `a fire`. The one thing the folder supplies, `utility_phone`, is checked again against a plain-phone pattern with `preg_match` before it joins the sentence, so even a value that got past the sync cannot add words to the safety message.
- One row, three owners of the decision, and a lock that cannot be skipped (plan 02-22): approving a held draft does not create a new message; `OutboundSender::sendExisting()` turns the same `messages` row from `draft` to `queued` to `sent`, and records who decided in `resolution`, `resolved_by` and `resolved_at`, keeping the agent's own words in `original_body` when the owner changed them. The claim is `DB::transaction(function () { $draft = Message::query()->lockForUpdate()->find($id); if ($draft->status !== MessageStatus::Draft) { return false; } ... })`: `lockForUpdate()` makes a second request for the same row wait, and the status test inside the transaction means a draft that a newer text replaced, or that another tab already sent, is refused with a sentence instead of going out twice. In `ConversationThread`, `#[Locked] public ?int $draftId` tells Livewire that only server code may change that property; a browser that tries to set it gets an exception, so the owner's page cannot be pointed at some other conversation's draft. `render()` calls `syncDraftFields()` each time the page redraws (including the 5-second poll), so a newer draft fills the box unless the owner has already typed in it, in which case their words stay and the assistant's new draft is shown above.
- Alpine in Filament views (plan 02-23): Alpine is the small JavaScript library Filament already loads on every page, and an attribute like `x-init="$el.scrollTop = $el.scrollHeight"` on the thread's box runs once when that box first appears. `$el` is the element itself and `scrollHeight` is the full height of everything inside it, so setting `scrollTop` to it scrolls the box to its bottom, which is how a phone opens at the newest text. The 5 second refresh does not run it again, so the owner is not yanked down while reading older messages.
- Filament table widgets (plan 02-23): `app/Filament/Widgets/DraftsWaiting.php` is a small table on the home screen. It `extends TableWidget`, its `table()` method sets the heading, the query and the columns, and the panel finds it by itself because `discoverWidgets(in: app_path('Filament/Widgets'))` scans that folder, so there is no list to keep up to date (the old stock widgets were removed by deleting the `->widgets([...])` list). `$sort` puts the widgets in order on the page, `$columnSpan = 'full'` gives each the whole row, and `$isLazy = false` draws the table with the page instead of a moment after it. One thing to watch: a time in the database is stored in the app's zone, so "today in the business's zone" in `TodaysConversations` finds the day's start and end by the business clock and then converts both edges to the app zone before asking the database.
- A date column as a yes-or-no flag, and one place that says no (plan 02-24): `contacts.sms_opted_out_at` is a nullable timestamp, so "has this person opted out?" and "when?" live in one column, and `Contact::isOptedOut()` just asks whether it is filled in. The `datetime` cast in `casts()` turns the stored value into a Carbon date object, which is what lets `OutboundSender::whyBlocked()` shift it into the business's time zone and print `M j` ("Oct 13"). `OutboundSender` now asks for `ActiveConfig` in its constructor; Laravel's container sees the type and hands one over, so nothing that already calls `app(OutboundSender::class)` changed. A STOP text is stored already marked as dispatched and handled (`dispatched_at` and `handled_at` set when the row is created, inside the same transaction as the opt-out), so the queue, the sweep and the front desk all treat it as finished work, and `handle()` returns early before the safety check and the queue.
- `match` for a small decision, and an exception that remembers its cause (plan 02-25): `TextKeywords::actionFor()` ends in `return match ($type) { 'STOP' => 'stop', 'START' => ..., 'HELP' => 'help', default => null };`. A `match` is a `switch` that gives back a value, compares strictly and needs a `default`, so the whole decision "what does this text do?" fits in one expression you can read top to bottom. The word lists are `public const array` on the class, so the same list serves the real code and the tests, and the comparison happens in PHP with `mb_strtoupper(trim($body))`, never in SQL, because `LIKE` is case-sensitive on Postgres and not on SQLite. When the carrier refuses a number that opted out, the channel throws `RecipientOptedOut`; `OutboundSender` catches that one before its general `catch (Throwable $exception)`, because PHP tries the `catch` blocks in order and takes the first that fits. It then throws a plain `DomainException` the owner can read, with `previous: $exception` so the original is still attached, and `RunFrontDesk` asks `$exception->getPrevious() instanceof RecipientOptedOut` to tell this refusal from other failures without comparing sentences.

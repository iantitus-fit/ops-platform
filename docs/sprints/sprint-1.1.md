# Sprint 1.1: Faster Answers

Status: in progress. `.planning/` is the plan of record: this file is the
sprint's acceptance list and the walk-through log, and phase 02.1 in
`.planning/ROADMAP.md` holds the plans.

## Goal

Routine questions finish without the owner. A price or an offer the owner wrote
goes out at once, sent by code and never written by the model. An easy answer
never waits behind a hard question that is already with the owner. A customer
who is waiting always hears back, in the owner's words, and is promised only
what the opening hours can keep.

## Notes for Phase 02.2

What `gate:export` (WR-09) and the Owner Loop must handle, because Phase 2.1 changed the data they read. `app/Console/Commands/GateExport.php` still exports only `agent_reply` messages with a stored verdict, and `DraftResolution` has no idea yet that a draft can close without the owner. - New message kinds. `partial_holding`, `complaint_holding`, `discount_holding`, `check_in_reply`, `added_info_reply` and `code_answer` are fixed texts written by code from the owner's own lines. None is a front desk decision to label, and `gate:export` must say which of them it leaves out and which it keeps. `code_answer` (a price or offer sentence sent by code, Jev skipped) is the one the export most likely needs as its own row, because it is the new way a price leaves without the owner.
- A new draft resolution. `answered` means a price draft was closed because a price sentence for the service it waited on went out. The export has to read it as neither approved nor discarded: the owner never acted.
- `agent_reply` texts that carry owner sentences. An `agent_reply` can now begin or end with the owner's price sentences or offer sentences, and its `meta['parts']` lists what the text was made of (the code sentences, the model's words, one fixed line), with `meta['price_sentences']` (slug, key and amounts in cents) and `meta['offers']` (offer slugs) naming the sentences. Any measure of what the model wrote must count only the model's part, or the export credits the model with the owner's words.
- Drafts with an empty body. A price or discount question code could not answer (`price_policy: none`, a service not in the folder, a sentence that could not be sent) is stored as a draft with no words, held as `price:no_sentence` or `send_refused`. The owner writes the answer. The export has to keep the owner's text, not read the empty draft body as "the model wrote nothing".
- Drafts replaced under a chain. `meta['replaces']` lists the earlier drafts a fresh draft covers, and `meta['first_reply']` keeps the first model reply a whole-thread draft replaced (plan 02.1-14), so the labeled data has both sides of that case.
- A new stop reason in the verdict. A hold now names why in plain words (D-40), including the hold reasons added by this phase, so the export's reason column has values it has not seen.
- Carried items from CONTEXT for the Owner Loop itself: a reply code for a draft with newer customer messages must not send blindly (the "customer wrote again since this draft" line is only a warning on the screen today); the "handled" follow-up must cover drafts auto-closed as `answered`; the customer update past the holding reply's promise ships together with the owner re-alert; and the fallback classifier question (an alternate driver chosen per business, or a runtime fallback when Jev fails, which changes what "fail closed" means and must also get message text only).

## Walk-through log

One line per concept, added the first time it shows up in this sprint.

- A test that grows with the code (plan 02.1-01): in `HoldingReplyTest`, `->with(fn (): array => array_combine(array_map(fn (MessageKind $kind): string => $kind->value, MessageKind::startsWait()), array_map(fn (MessageKind $kind): array => [$kind], MessageKind::startsWait())))` gives the test one row per kind that starts a wait, named by the kind's text. The list comes from the enum's own `startsWait()` method, so a kind added to that list later is tested the moment it is added, and if `holdingAlreadySent()` forgot it, that row fails. The dataset is a closure, not a plain array, so Pest only asks the enum when the test runs.
- A setting that is allowed to be missing (plan 02.1-03): `'check_in_hours' => 'bail|sometimes|integer:strict|min:1|max:12'` in `Validator::rulesFor()` uses `sometimes`, which tells Laravel's validator to run the other rules only when the field is present, so an owner who leaves the line out gets no error and the check-in time stays off, while `check_in_hours: two` or `0` or `13` is refused in plain words. `integer:strict` accepts only a real number from the file, not the text `"2"`. The reply check then asks `($file->frontMatter['check_in_hours'] ?? null) === null`: `??` gives `null` for a missing key without an error, so the same line covers both absent and empty. On the sending side `FixedReplies::render()` hands `strtr()` a list of `{fill_in}` => words pairs and it swaps every one in a single pass, so words that were just inserted are never searched again for more braces. `BusinessClock::checkInPhrase()` adds hours to the next opening with `$opening->addHours($hours)` and compares two times with `>` (Carbon objects compare by the moment they name), and a check-in past closing time becomes the closing time itself.
- A model answer that is allowed to be wrong (plan 02.1-05): in `FrontDeskAgent::schema()`, `$schema->boolean()->nullable()->required()` tells the model every field must be present but may be `null`, and `$schema->array()->items($schema->string())->required()` is a list of plain texts. The model's answer is untrusted, so in `AgentReply::fromStructured()` the six new fields are read by small private readers that never throw: `($data['asks_discount'] ?? null) === true` is true only for a real boolean true (the `??` gives `null` for a missing key without an error), `in_array($value, ['check_in', 'added_info'], true)` accepts only those two words, and `ReplyLabel::tryFrom()` returns `null` instead of an error for a word that is not a label. A wrong answer falls back to the safer path instead of costing a provider attempt. On the prompt side, `FrontDeskPrompt::instructions()` got a third argument written `?Message $waitingDraft = null`: the `?` means "a Message or nothing", and the `= null` default means every older call that passes two arguments still works.
- Checks a rule string cannot say (plan 02.1-06): `Validator::rulesFor()` handles the shape of a price sentence with Laravel's own rules (`price_sentences.*.sentence` is `required|string`, `price_sentences.*.amounts_cents.*` is a whole number), but "the dollar amounts written in the sentence must equal the amounts the file declares" compares two values, so it lives in a plain method, `priceSentenceErrors()`, that runs beside the rules and adds its own lines to the same report. Amounts stay integer cents all the way: `CodeChecks::dollarAmountsInCents()` reads `$2,000` as `200000` with `(int)` and string padding, the two lists are compared as sorted lists of integers with `!==`, and `dollars()` turns cents back into `$2,000` or `$89.50` with `intdiv()`, `%` and `number_format()`, never a float. The service-name check lower-cases both sides with `mb_strtolower()` (the multibyte version, so accented letters fold too) after `Str::squish()` collapses runs of spaces, so `AC  REPAIR` still finds `AC repair`.
- Dates compared as text (plan 02.1-07): an offer's `start_date` and `end_date` are checked by Laravel's own rule, `'start_date' => 'bail|required|date_format:Y-m-d'`, which accepts only a year-month-day date with dashes. Once both are known to be in that form, `Validator::offerFileErrors()` compares them as plain strings with `$end < $start`, because `2026-09-30` sorts before `2026-10-01` letter by letter exactly as the days do; no date objects are needed. `isCalendarDate()` first rebuilds the value with `DateTimeImmutable::createFromFormat('!Y-m-d', ...)` and checks it prints back the same, so `2026-02-30` is not mistaken for a date. In `FolderSync::compile()` the new `'offer' =>` arm of the `match` stores each file under its slug (`$compiled['index']['offer'][$slug] = $path`); without that arm the `default` arm would keep only one path for the whole type, so a second offer would silently replace the first.
- Naming a result with a small value class (plan 02.1-08): `PricePick` is a `readonly class`, so once it is built nothing can change a property, and its constructor is reached through named builders (`PricePick::send(...)`, `PricePick::hold($slug)`) instead of one long argument list, so a line like `PricePick::hold($slug)` reads as what it means. `ReplyParts::kind()` uses `match (true) { ... }`, which walks its arms top to bottom and returns the value of the first arm whose condition is true; that is how "a complaint line wins, then the partial holding line, then the model's words" is written in the order it applies. In `RunFrontDesk`, `array_filter(..., fn (PricePick $pick): bool => $pick->isSend())` keeps only the picks that send, and `array_map` turns them into plain sentences; `Cache::lock()` in the new test holds the same lock the sender waits for, which is how the test makes a send get refused.
- Newest row wins, and a relation's order trap again (plan 02.1-09): `RecordIntakeAnswers::currentFor()` reads a conversation's answers oldest first and calls `->keyBy('question_key')`; when two rows share a key, `keyBy` keeps the later one, so a corrected answer replaces the earlier one without any delete, and the earlier rows stay as history. The same plan hit the trap from plan 02-37: `Conversation::messages()` already sorts oldest first, so a newest-first lookup ("what did the last run leave pending?", "what price sentence did we send last?") needs `->reorder()->orderByRaw('coalesce(sent_at, created_at) desc')->orderByDesc('id')` first, or it quietly returns the oldest message; the tests only caught it once a conversation had three outbound texts. `->lazy()` after that reads the rows in small chunks and `->first(fn ...)` stops reading at the first message that fits, so a long thread is not loaded whole. `PriceSentencePicker::direction()` compares two lists of integer cents with `match (true)`: equal sorted lists are `same`, a new lowest at or above the old highest is `higher`, a new highest at or below the old lowest is `lower`, anything else overlaps and is `changed`, so `$2,000 to $5,000` followed by `$5,000 to $10,000` still reads as going up.
- Comparing ids, not clocks (plan 02.1-10): `ConversationThread::customerWroteAgain()` is a `#[Computed]` property, so the view reads it as `$this->customerWroteAgain` and Livewire works it out once per request. It asks the database one yes-or-no question with `->exists()`: is there an inbound message in this conversation whose `id` is above the largest id in the draft's `meta['in_reply_to']` list (`max(...)` of the ids the draft answered)? It does not compare with the draft's own id or time, because a text that arrives while the front desk is still writing gets a lower id than the draft yet was never in the burst the draft answered. Ids only grow, so "above the newest id the draft answered" means "arrived after that text".
- Whole days in the business time zone (plan 02.1-10): `BusinessFolder::staleOfferWarnings()` builds today with `CarbonImmutable::now($timezone)->startOfDay()`, so "today" is the date on the wall in Chicago and not in UTC, and builds the cut-off from the offer's start the same way with `->addDays(90)`. An offer warns only when that cut-off date is before today's date, so day 90 is quiet and day 91 warns. It compares two dates directly instead of subtracting and reading a signed `diffInDays` number (which is a float and changes sign with the order of the two dates). `CarbonImmutable` returns a new date from each call and never changes the one it was called on, so `$today` stays safe to reuse inside the loop.
- One list, named once (plan 02.1-11): `SendFixedReply::COMPLAINT_CODES` is a class constant, `public const array COMPLAINT_CODES = [...]`, so the three reason codes that mean "complaint" are written in one place and any other class reads them as `SendFixedReply::COMPLAINT_CODES` without making an object first. `RunFrontDesk::alertReasonFor()` used to carry its own copy of that list; now it and the new per-reason `holding()` both read the one constant, so the alert and the holding reply can never disagree about what a complaint is. `in_array($code, self::COMPLAINT_CODES, true)` passes `true` as the third argument so the match is strict (the same type and value, not a loose "looks equal"). Separately, `RunFrontDesk` now asks for an `OfferSentences` in its constructor; Laravel's container sees the type and builds one itself, handing `OfferSentences` the `ActiveConfig` it needs in turn, so no line anywhere has to say `new OfferSentences(...)`. `OfferSentences::liveToday()` takes today as `CarbonImmutable::now($timezone)->toDateString()`, a `2026-12-31` text in the business's zone, and compares it to the offer's dates as text, so an offer is still live at 11:30 pm on its last day in Chicago even though UTC has already turned to the next day.
- One method, three possible answers (plan 02.1-12): `RunFrontDesk::sendPassingReply()` is declared `: Message|Verdict|null`, a union return type, because a send can end three ways and the caller must tell them apart: the `Message` that went out, `null` when the failure was already raised to the owner, or a `Verdict` held as `send_refused` that the caller turns into a draft. The caller checks `$sent instanceof Verdict` to see which one it got. The same plan uses the null-safe `?->` in `$verdict?->lifeSafety`, which gives `null` instead of an error when `$verdict` is `null`, because a run that sends only owner sentences has no verdict to read.
- Reading a stored record instead of asking the model (plan 02.1-13): `HeldReasons::priceAlone()` is a `public static function`, so `HeldReasons::priceAlone($draft)` is called on the class with no object made first.
